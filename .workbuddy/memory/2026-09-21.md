## 内存 WMI 兜底段错误（memory.wmi 源）定位与修复（17:00–17:25）
背景：新增 `memory_wmi.rs`（`Win32_PhysicalMemory` 兜底补内存频率/型号，修"无盘客户机没有内存频率"）后，
`--selftest` 跑 `memory.wmi` 源 **EXIT=139（段错误 / STATUS_HEAP_CORRUPTION）**。

### 根因（两阶段，缺一不可）
1. **早期 drop（先修）**：`wmi_connect` 最初把 `ComGuard` 绑成局部 `let _com` 并在函数返回时析构
   → `CoUninitialize()` 在 `wmi_query` 运行**前**拆掉 COM → 对 `svc` 代理的 `ExecQuery/Next` 访问违规。
   修法：`wmi_connect` 改为返回 `Option<(IWbemServices, ComGuard)>`，`query_wmi_memory` 用
   `let (svc, _guard) = wmi_connect(...)?;` 持有 guard 到查询全部完成。
2. **CoUninitialize 拆公寓（真凶）**：即使 guard 活到查询结束，它在 `query_wmi_memory` 返回时 Dropped
   会 `CoUninitialize()`，**此时 `rows`/`svc` 等 COM 对象尚在作用域内正被 Release** → 公寓被拆 + 对象释放
   交叉 → 堆损坏/AV。`physical_disk.rs` 之所以不崩，是它的 `ComGuard` 放进 `OnceLock` **从不反初始化**。
   修法：`ComGuard { own: false }` —— COM 只初始化、进程退出由 OS 回收（与 physical_disk.rs 等效），guard 仍
   返回并持有以挡住第 1 阶段。**关键纪律：WMI 源的 COM guard 绝不能在本源函数内 `CoUninitialize`。**

### 顺带确认的正确点（易误判）
- `VariantToStringAlloc` 返回 `windows_core::PWSTR`（非 BSTR），用 `CoTaskMemFree` 释放是**对的**，
  不是双释放（PWSTR 无 Drop）。这条与 physical_disk.rs 一致，不是根因。

### 验证（不可造假）
- `WSX_TRACE=1 WSX_WMI_DEBUG=1 ./winsuitex.exe --selftest`：**EXIT=0，自检 12/12 通过**，
  `memory.wmi` 前后堆均为 ok，wmi_debug.log 走到 `set_memory_sticks 完成`。
- 全量采集 `--json` 也 EXIT=0、JSON 正常写出。
- 门禁三项全绿：fmt / clippy(`--workspace --all-targets --all-features -D warnings`) / test（119 用例，含 7 个 memory_wmi 单测）。

## 键鼠分类修复：G402 鼠标误判为 Keyboard（18:10–18:16，段 3 附）
Z.W. 确认单独排查：`input_devices` 里 G402 鼠标 `kind: Keyboard`（和 B930 一起并到键盘类）。
