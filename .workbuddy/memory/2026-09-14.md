## 根因修复（防复发）

- **成因**：`build.bat` 若在 Git Bash 下被 `bash build.bat` 执行，`chcp 65001 >nul` 会被 bash
  当成"重定向到文件 nul"，从而写出保留设备名垃圾文件。cmd 下 `>nul` 本身完全合法，故不改它。
- `build.bat`：首行加 polyglot guard
  `:; if [ -n "$BASH_VERSION" ]; then echo "..."; exit 1; fi`
  bash 下 exit 1 并提示；cmd 下是标签行，不执行。已在临时目录实测：exit=1 且无 nul 生成。
  ⚠️ 未在真实 cmd.exe 下实测（沙箱禁用 cmd）；若异常，删掉第 1 行即回退。
- `build_git.sh`：原写死旧路径 `/d/project/WorkBuddy/内置工具/WinSuiteX`（项目已搬到
  `D:\project\WorkBuddy\WinSuiteX`，跑起来直接 exit 1），改为 `cd "$(dirname "$0")"`。
- `.gitignore`：新增 `nul` / `con` / `aux` / `prn` 兜底，杜绝误提交。

## Rust 重构评估（产出 RUST_REFACTOR_ASSESSMENT.md）

- 系统性梳理：项目结构 / 功能清单 / 依赖 / 迁移风险 / 优先级，报告 446 行。
- **关键结论（后续做迁移决策时直接复用）**：
  - 项目**无多线程**（仅 WM_TIMER）、**无 WMI**（走 SMBIOS/CPUID/SetupAPI/IOCTL）、**无运行时配置文件**（状态全在注册表）。
  - **「玻璃拟态」是纯自绘**，非 DWM 玻璃：无 DwmExtendFrameIntoClientArea /
    SetWindowCompositionAttribute / UpdateLayeredWindow / WM_NCCALCSIZE。→ UI 层可逐条等效重写，
    难度是工程量而非技术不可行。
  - **COM 注册真相**：DllRegisterServer/DllUnregisterServer 是**空实现**（仅返回 S_OK），
    全仓无 regsvr32 调用；注册全由管理器写注册表。非手写 vtable，用系统 shobjidl.h 定义。
  - **libcpuid FFI 面极小**：仅 2 函数（`cpuid_get_raw_data`/`cpu_identify`）+ 2 个 POD 结构体
    （无 union/位域）。不可用 raw-cpuid/sysinfo 替代——代号库 471 条（Intel 261 + AMD 210）是核心价值。
  - **最大 unsafe 面 = SMBIOS 手工解析**（pack(1) + 柔性数组 + 未对齐读），失败是 UB 非降级。
  - **测试缺口**：selftest 覆盖注册表/COM 结构，但**硬件采集零断言**；UI 绘制完全无测试。
  - 推荐首个里程碑：单迁 `--report` 无头路径，新旧二进制导出 HTML 逐字段对拍（不碰 UI）。
  - 存量隐患：`EnsureShellDll(FALSE, perUser)` 的 force **恒为 FALSE** → 已有 DLL 永不覆盖（升级未启用）。
- **发现并修复真 bug**：`build.bat` 链接缺 `-lgdiplus`（main.cpp 用 24 处 GDI+ 符号且无 pragma
  comment 补链）→ cmd 下链接必失败；现有 exe 都是 build_git.sh 编的所以没暴露。已补上。
- **待 Z.W. 确认**：`hardware.cpp:1100` `g->vramMB = 0;` 疑笔误（注释说"留 DXGI 值"），
  迁移前需确认意图，否则会把 bug 一起翻译过去。

## Rust CPU 代号识别：GitHub 调研 + cpuid.rs 重写（用户显式请求）

- **用户诉求**：C++ 版硬件识别不准确（E3-1230 V2 被错判为 Bloomfield 而非 Ivy Bridge），
  要求在 GitHub 上搜更精确的识别算法，完善 Rust 版以提升**准确率 + 稳定性**。
- **关键结论（先于改码，先调研后动手）**：
  - Rust 现有表其实**早已把 Ivy Bridge 写对**（model 0x3A → Ivy Bridge），错的是 **C++ 版**当年写错。
    故 Rust 侧真正的缺口是「表陈旧 + 缺混合架构感知」，不是算法错。
  - **权威数据源**（交叉核对）：Intel SDM Vol.4 Table 2-1、LibreHardwareMonitor `IntelCpu.cs`、
    fuchsia `zircon/kernel/lib/arch/cpuid.cc`、siomon `cpu_codenames.rs`；AMD 用 ZenStates-Core / wikichip / siomon。
  - **family/model 公式**（Intel & AMD 通用，与 SDM/lbpucpuid/fuchsia 一致）：
    `family = base_family==0xF ? base_family + ext_family : base_family`；
    `model  = (base_family==0x6||0xF) ? (ext_model<<4)|base_model : base_model`。
  - **Intel 混合架构（12 代+）**：`CPUID.07H:EDX[15]` = Hybrid 标志位；标注 `hybrid` 后缀。
- **改动文件**：`rust/crates/winsuitex-platform/src/cpuid.rs`
  - 大幅扩展 `TABLE`：补全 Intel 2017+ 全系（Tiger/Rocket/Alder/Raptor/Meteor/Lunar/Arrow Lake、
    Sapphire/Emerald/Granite Rapids 服务器线）+ AMD Zen 2~Zen 5（Renoir/Matisse/Genoa/Raphael/Phoenix/Granite Ridge/Turin/Strix 等）。
  - 新增 `cpuid_family_model_stepping()`（修正原无条件 `(xmodel<<4)|base_model` 的算法缺陷，加门控）、
    `intel_is_hybrid()`；重写 `cpu_codename()` 走查表→品牌后缀→混合标注。
  - **删除死代码 `refine_kaby_family()`**：真实 Intel 品牌串（如 `i7-8565U CPU @ 1.80GHz`）根本不含
    "Whiskey"/"Amber"，该函数永远触发不到——属永不生效的误导代码，已删。8/9 代 Whiskey/Amber 与
    Kaby/Coffee 共用 (family,model)，纯靠 CPUID 无法区分，需解析品牌型号数字，列为后续可选增强（未做）。
  - ⚠️ **残余风险**：Zen 5 display model 各来源矛盾（siomon 给 0x20/0x24、wikichip 0x40、ZenStates 0x44），
    当前采 siomon 值（32/36）；真实 Zen 5 机器无，未硬验证。
