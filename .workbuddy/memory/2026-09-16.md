## #2 真机数据暴露的新问题 + 修复（3 处）

### 2.1 内存 part_no 乱码（严重，已修）
`ChannelB-DIMM0` 的 `part_no` 是 18 个 U+FFFD（hex `efbfbd` ×18）。
排查确认**不是解析 bug**：Type17 偏移 0x1A 正确、空槽识别正常、同结构 vendor="Kingston" 读对了
—— 是**固件本身在这根内存的 Part Number 填了 18 字节非法 UTF-8**（OEM 内存常见）。

- 根因：`smbios.rs::str_at` 用 `String::from_utf8_lossy` → 非法字节变 U+FFFD → 报告显示 `??????????????????`
- 修法：`std::str::from_utf8(raw).ok()?` 严格解码，失败即整串丢弃（报告显示"未知"）。
  **不截断取前半段**：含非法字节的串几乎总是整串 junk，截半会产出"看着像型号其实是错的"值，误导资产盘点。
- 新增测试 2 个：`invalid_utf8_string_is_dropped_not_replaced` / `str_at_basics`（core 测试 19 → 21）
- **报告层兜底**：`winsuitex-report` 新增 `usable()`，含 U+FFFD 一律按未知/`-` 渲染。
  用带乱码的**旧** inventory.json 渲染验证：输出里 U+FFFD 出现 0 次，显示 "Kingston 未知"。

### 2.2 键盘显示"未知输入设备"（已修）
真机键盘 VID 1A2C:6004，HID 产品串拿不到、品牌表未收录 → 落到兜底分支显示"未知输入设备"。
- `hid.rs`：新增分支 `(None, Some(v), Some(p)) => format!("未知输入设备 ({v}:{p})")`，带上 VID:PID 可查
- `peripheral_db.rs`：补 4 个**已核实**的 ODM VID（均标厂商名而非零售品牌，避免误报）：
  `1A2C` SEMICO 华润上华、`1C4F` SiGma Micro、`062A` MosArt、`04F2` Chicony 群光；
  并加中文显示名。`248A` 本次未查到确证 → **主动放弃**，宁可留空不标错。

### 2.3 build.rs 编译时间戳被 cargo 缓存（已修）
emit 了 `rerun-if-changed=build.rs` 后，cargo 就只按清单判断；改了采集代码却不重跑构建脚本
→ 时间戳不更新 → 又变成"分不清新旧 exe"。
修法：显式列出 `src` + 三个兄弟 crate 的 `src` 目录。验证：时间戳从 23:39:10 刷新到 23:56:09。

### 2.4 crashtest.bat 两个显示 bug（已修，仅诊断脚本）
- `crash.json =  bytes`（空）：把 set/for/echo 放在同一个 `if(...)` 块里，`%JSZ%` 在解析整块时就展开
  → 批处理经典延迟展开陷阱。改成 goto 结构绕开。
  （`inventory.bat` 同样的语句在块外，所以正常显示 5819 bytes。）
- `type crash.err` 中文乱码：exe 写 stderr 是 UTF-8 字节，cmd 默认 936 解释。
  type 前 `chcp 65001`、打完 `chcp 936` 还原，bat 自身的 GBK 中文 echo 不受影响。

## 复用教训
- **`emit` 了 `rerun-if-changed` 就等于接管了 cargo 的脏检查** —— 少列一个目录，构建脚本就不重跑。
  想让"编译时间戳/版本号"真实反映代码变化，必须把所有相关源码目录列全（或用环境变量兜底）。
- **lossy 转换是静默的数据污染源**：`from_utf8_lossy` / `to_string_lossy` 会把损坏数据变成 U+FFFD
  一路带进客户报告。采集层应严格解码 + 失败即丢弃；渲染层再加一道 `contains('\u{FFFD}')` 兜底，
  两层都堵住，新采集源再犯同样错误也不会污染输出。
- 批处理：`if (...) 块内 set + 用 %VAR%` 必踩延迟展开。要么 `enabledelayedexpansion` + `!VAR!`，
  要么改 goto 结构把语句移出块 —— 后者不依赖额外 setlocal 选项，更稳。

### 7.2 显示器厂商内联（去掉独立成列）
`display` 文本段 + HTML 段原本各有一条**独立**的 `| 厂商 AOC (冠捷)` / `厂商：AOC (冠捷)` 行。

```rust
let name = d.name.clone().unwrap_or_default();
let mut label = name.clone();
if let Some(v) = &d.vendor {
    if usable(v) {
        let zh = vendor_zh(v);
        if name.is_empty() {            // 没型号名时退化为厂商名（带中文）
            label = v.clone();
            if zh != *v { label.push_str(&format!(" ({zh})")); }
        } else if zh != *v {            // 有型号名：型号 (中文)
            label.push_str(&format!(" ({zh})"));
        }
    }
}
```
覆盖 4 种情况：有名有中文 / 无名有中文 / 有名未收录(无名) / 无名(空) 全部合理。
序列号 / 生产周年仍独立成行（用户只要求厂商内联，序列号不在本次范围）。

## #36 自动地址标注：区分「人工配置的业务 IP」与「系统自动兜底地址」

### 全面审查（用户："不要光看网卡，全面审查"）— 4 个数据层 bug 已修
审查方式：两路子 agent 并行（采集层扫哨兵/单位；渲染层做 JSON↔HTML 全字段比对），**每条结论我都回源码逐条验证过才动手**，不盲信 agent 报告。

**P0-1 内存容量 0x7FFF 哨兵（`smbios.rs` parse_mem）** ★本次最严重
- 现象：8 根条 `capacity_mb` 全是 `32767`，而 `total_mb=524191`。8×32767=262136，与总计差一倍。
- 根因：SMBIOS Type 17 的 Size(0x0C) 是 16 位，单条 >32GB 放不下，固件置 **0x7FFF** 并把真实容量放进 Extended Size(0x1C, DWORD, 单位 MB)。原代码只在 `size_word == 0xFFFF` 时读 Extended Size，**漏了 0x7FFF**，于是把哨兵当真实值。
- 佐证：Linux `drivers/firmware/dmi_scan.c` `dmi_memdev_size()` 三分支同理 —— `size & 0x8000 → KB`；`size != 0x7FFF → MB`；**否则 Extended Size**。真机 8×64GB → 修复后 65536 MiB/根，8×65536=524288 vs 524191 差 0.018%（系统保留），完全吻合。
- **C++ 参考实现 `hardware.cpp:222-229` 有完全相同的漏判**，需同步修（Rust 只是忠实移植）。

**P0-2 EDID 物理尺寸读了错字节（`edid.rs`）**
- 详细时序描述符里：`b+12`/`b+13` = 宽高 mm 低 8 位，**`b+14` = 高位 nibble**。代码却从 **`b+11`** 取高位 —— b+11 是 V/H 同步信号 offset/pulse width 的高 2 位，与尺寸无关。
- 后果比"取不到"更糟：常见 `b+11=0x2x` 时算出 530×270mm → 23"，**落在 (10..=120) 合理区间内，输出一个很像真的错值**。这解释了历版 `size_inch` 为何时有时无。
- **测试夹具是按错误实现写的**（`e[65]`=b+11 放 0x21），等于给 bug 背书 → 已把高位移到 `e[68]`（b+14），数值断言 531×299mm/24" 不变。新增回归测试：b+11 有值、b+14 为 0 时必须判 None。

**P0-3 EDID 序列号大小端反了**：规范 bytes 0Ch-0Fh 是 **LSB first**，代码用 `from_be_bytes`。仅当显示器带 0xFF ASCII 序列号描述符时才碰巧正确。已改 `from_le_bytes` + 排除 `0xFFFF_FFFF`，新增字节序回归测试。

**P0-4 CPU core/thread 缺 0xFFFF 哨兵（`smbios.rs` parse_cpu）**：SMBIOS 3.0+ 的 Core Count 2(0x2A)/Thread Count 2(0x2E) 的 `0xFFFF` 表示"未知"，只过滤 0 会输出 **65535 核**。C++ `hardware.cpp:205,209` 有 `!= 0xFFFF`，Rust 移植时漏了。

**报告层三处**：
- 显存 `(vram.0 + 512) / 1024`：256 MiB → **"0 GB"**，512 MiB → 虚报 "1 GB"。已改走 `fmt_mb`。
- 容量口径校验硬编码"可能含核显/预留内存，**属正常**"：真机偏差 50% 被这句话洗白。已按偏差率分档（≤2% 静默 / 2~10% 温和 / **>10% 告警并给百分比**），阈值提为 `DIFF_IGNORE_RATIO`/`DIFF_ALERT_RATIO`。

3. **硬盘段补序列号**：原来只在分区表经 `serial_cell` 间接带出，**未分配 / 无卷的盘序列号永远不可见**，而序列号是换盘唯一凭据。
4. **分区表加"已用（百分比）"**：巡检时"这盘快满了没"比绝对容量更需要一眼看到；`可用 > 总量`（配额/挂载点异常口径）时不硬算，给 `-`。
5. **表头 `NT 设备名 / 磁盘` → `物理磁盘`**：`pd_str()` 实际输出的是 `\\.\PhysicalDriveN`，是物理磁盘路径不是卷的 NT 设备名，名实不符。
6. **内存段加「插槽占用 8 / 24 槽已插」汇总**：真机上立刻看出 24 槽只枚举到 8 根，是容量口径对不上的直接线索。
7. **DDR4 频率 `2400 MHz` → `2400 MT/s`**：SMBIOS 的 Speed/Configured Memory Speed 是**传输率**，DDR4-2400 的实际时钟是 1200 MHz。标 MHz 是行业惯例（任务管理器也这么写），本工具选准确。**CPU 的 `speed_mhz` 是真 MHz，未改。**

### 硬盘通电时间 / 健康度（SMART）——调研结论：**两版都没实现，且必须管理员**
用户问"能不能准确拿到"。子 agent 调研 + 我自己 grep 双重确认：
- **C++ 老版没有**：`hardware.cpp` grep `SMART|PowerOn|通电|健康|IOCTL_ATA|PASS_THROUGH` 全部无命中（只有文档里的否定句）。
- **Rust 新版没有**：`PhysicalDisk` 只有 6 字段（index/model/iface/media/serial/size_bytes），全项目无 SMART 代码。
- **权限是硬门槛**：`crates/winsuitex-platform/src/physical_disk.rs:373` 现在用 `open_device(path, GENERIC_READ.0)` —— 只**读**权限。而 SMART 的 `IOCTL_ATA_PASS_THROUGH` / `IOCTL_SCSI_PASS_THROUGH(_DIRECT)` 需要 **GENERIC_READ|GENERIC_WRITE + 管理员**。且该文件第 12 行注释自己写着"**本工具常在非提权下运行**，CreateFileW 打开失败必须降级为 None" —— 这是核心矛盾。
- **分介质可行性**：SATA/AHCI → ATA pass-through 读 attr 9（Power_On_Hours）；NVMe → `IOCTL_STORAGE_QUERY_PROPERTY` + `StorageDeviceProtocolSpecificProperty` 取 GET LOG PAGE 0x02（PowerOnHours / PercentageUsed / CriticalWarning）；**USB 外接盘**大多数桥接芯片拦截 pass-through → 拿不到；**RAID 卷下 / 虚拟盘 / 网吧无盘客户机** SMART 不可见。
- **落地建议（未实现，留待用户决策）**：分四层（NVMe → SATA → USB → 兜底），拿不到时**明确显示"不可用"而非 0 或空**（编造 0 会让"通电 0 小时"看起来像新盘，比没有更危险）；字段建模建议 `Option<u32>` 通电小时 + `Option<u8>` 健康百分比 + 明确的"数据不可用"枚举态。
- ⚠️ 对网吧场景的现实判断：**无盘客户机没有本地盘，SMART 无意义**；价值集中在服务器与有盘机器，但批量巡检若非管理员运行则整体拿不到 —— 做之前要先定"是否强制提权"。

### 硬盘 SMART 已实现（用户拍板"动手"）+ 对抗式审查抓出的 2 个 P0
**实现**：`model.rs` 新增 `DiskSmart` / `HealthStatus` / `SmartSource`（`PhysicalDisk.smart: Option<DiskSmart>`）；`physical_disk.rs` 新增 `query_smart` 按接口分流（NVMe → `IOCTL_STORAGE_QUERY_PROPERTY` + `StorageDeviceProtocolSpecificProperty` 取 LID 0x02 log page；SATA → `IOCTL_ATA_PASS_THROUGH` SMART READ DATA；USB/RAID/iSCSI/虚拟盘 → 直接给原因）；`report/lib.rs` 新增 `disk_smart_text`，拿不到时显示"不可用（原因）"。**SMART 用独立的 `GENERIC_READ|GENERIC_WRITE` 句柄**，绝不动原有 `GENERIC_READ` 只读路径（那是非提权也能采到型号/容量的关键）。

**★ 对抗式审查救了这个功能 —— 两个 P0 都会产出"看起来完全正常的假数据"**（我到 windows crate 源码 `src/Windows/Win32/System/Ioctl/mod.rs:6338` 核实后自己修的）：
1. **P0-1 NVMe 输出缓冲少算 8 字节头**：`IOCTL_STORAGE_QUERY_PROPERTY` 的输出是 `STORAGE_PROTOCOL_DATA_DESCRIPTOR = Version(4) + Size(4) + STORAGE_PROTOCOL_SPECIFIC_DATA(40)` = **48** 字节，代码只按 SPSD 的 40 算。后果二选一：驱动要 560 只给 552 → `ERROR_INSUFFICIENT_BUFFER`，**NVMe 永远显示"不可用"**；或某存储栈成功返回但数据错位 8 字节 → 温度/通电/健康全是假数值，**且全 0 哨兵因错位后字节非零而失效**。修法：缓冲改 `size_of::<STORAGE_PROTOCOL_DATA_DESCRIPTOR>() + 512`，并把定位逻辑抽成纯函数 **`locate_nvme_log(out, ret)`**（起点取回显的 `ProtocolDataOffset`，并校验 `offset >= 48 && offset+512 <= len && ret >= offset+512`）—— 抽成纯函数就是为了能写回归测试，否则这种 IOCTL 布局错误只能靠真机才知道。
2. **P0-2 无证据却判 Healthy 并算出"剩余 100%"**：盘不上报寿命字段时 `available_spare=0 && threshold=0 && critical=0`，原逻辑落到 `Healthy` 且 `health_percent = 100-0 = 100`。报告会渲染「健康 良好（剩余 100%）」——**把"没数据"伪装成"全新盘"，还带精确数值**。全 0 哨兵只挡整页全零，挡不住"字段未上报"。修法：`wear_reported = !(spare==0 && threshold==0)`，未上报时强制 `Unknown` + `health_percent=None` + `percentage_used=None`（Critical 优先级最高，即使未上报也要报）。

**顺带修**：失败路径 `source` 统一 `SmartSource::None`（原来失败也标 `NvmeLogPage`，下游按 source 判断"有数据"会被骗）；ATA 返回长度门槛从 `ret >= data_off+512` 放宽到 `ret >= data_off`（ATA pass-through 惯例只回结构体长度，原门槛会让 **ATA 盘恒不可用**）；`DiskSmart` 加 `#[serde(default)]`（否则将来加字段会让旧 JSON 的 smart 对象整体解析失败）。

**新增 4 条测试**：`locate_nvme_log_uses_descriptor_offset` / `rejects_short_buffer` / `rejects_offset_inside_header`（钉死 P0-1 的三种形态）、`nvme_wear_not_reported_is_unknown`（钉死 P0-2，故意写通电时间绕开全 0 哨兵以精确命中分支）。

**端到端验证**：`--json` 实采不崩溃（EXIT=0），本机是 **QEMU SAS 虚拟盘** → 正确返回 `source=None` / `health_status=Unknown` / `unavailable_reason="该接口不支持 SMART 直采"`，**通电时间是 `None` 而非 0** —— 纪律生效，无任何伪造数据。
