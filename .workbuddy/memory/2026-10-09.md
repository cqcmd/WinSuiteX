## 截图按钮 PNG 全透明 bug（真机反馈"截图没有内容"）
- 根因：GDI 的 `COLORREF` 只有 24 位色，`FillRect` 往 32bpp DIB 写 32 位时**高字节(alpha)恒为 0**；
  交给 GDI+ 的 `PixelFormat32bppARGB` 编码 → **全透明 PNG**：RGB 内容一分不少
  （实测 244 种颜色、白字 1.3 万像素都在），但看图器/微信/浏览器打开是一片空白。
  VM 里肉眼看图没发现，是因为读图工具忽略了 alpha。
- 修法：`save_png` 编码前把像素拷贝一份、每像素第 4 字节（BGRA 的 A）填 `0xFF`。
- 自行验证（不再靠肉眼）：新增 `tools/check_shot.py` —— 校验 alpha=255 占比 ≥99.9%、
  颜色种类 ≥20、白字墨水占比 ≥0.5%。修后实测：alpha 255 占比 1.0000、246 种颜色、
  白字 2.69%，exit 0。门禁全绿（fmt/clippy/274 tests）。
- 教训：GDI DIB → GDI+ ARGB 编码**必须**补 alpha；凡是"图看起来空白"先查 alpha 再查绘制。

## 第二十四轮：滚动后标题栏下方出现空玻璃横条（真机截图红框）
- 现象：真机（Win11，内容溢出滚动）滚动后，标题栏与页签行之间冒出一条**空的圆角
  玻璃横条**，把页签文字盖掉下半截；"系统"分组本体已滚出可视区。
- 根因：`fill_glass_round` 用 `SelectClipRgn`（默认 **RGN_COPY，整块替换**当前裁剪区）
  —— 把 on_paint 里 `IntersectClipRect` 设的可视区限制**整个逃掉**。第十九轮修
  "band 底色消失"时只对齐了 region 与视口偏移的坐标，没意识到替换裁剪区这层：
  滚出可视区的 band（SEC_H=30 亮带）照样在可视区外落像素；band 的图标/文字在
  `RestoreDC` 恢复可视区裁剪后又被裁掉 → 只剩空壳横条。
- 修法：`SelectClipRgn` → **`ExtSelectClipRgn(hdc, Some(hrgn), RGN_AND)`（相交）**。
  可视区内 band 照常画（第十九轮修复保持），滚出去的被裁掉。
- A/B 复现验证（VM 临时 WIN_H=500 才滚得动，滚 1 格）：
  - 旧（RGN_COPY）：空条**穿过页签行**，与真机红框一致 ✓ 复现
  - 新（RGN_AND）：页签完好、"系统"band 带图标标题正常 ✓ 修复
  - ⚠️ 复现技巧：滚 3 格滚过头（band 滚出窗口顶 y<0 不可见），必须**滚 1 格**
    让 band 恰好落在标题栏与页签之间（scroll≈82..126）。
- 三页回归（seq 硬件/右键/磁盘）全正常；还原 WIN_H=948；门禁全绿（fmt/clippy/274）。
- 教训：**SelectClipRgn 是替换不是相交**——凡在滚动变换内用 region 裁剪，一律
  ExtSelectClipRgn(RGN_AND)，否则裁剪区变成"全局有效"，会画到固定区。

## 第二十六轮：竖条拉到最下面时，截图/导出按钮失效（点击 + hover 同源）
- 现象：内容溢出滚动后，把竖条拉到最底下，点"导出报告"/"截图"两颗头部按钮**毫无反应**，
  鼠标移上去也**不高亮**（Z.W. 反馈"竖条拉到最下面时，截图和导出按钮失效"）。
- 根因（与点击、hover 完全同源）：头部按钮钉在**固定层**（不随滚动），命中几何是**屏幕坐标**；
  但 `on_mouse_move` 仍用 `let (btn, tb) = pages::hit_test(x, y)` 取 `btn`，其中 `y` 是
  **内容坐标** `y = screen_y - scroll_y()`（on_click 上一轮已先改对了，on_mouse_move 漏改）。
  滚动越多偏差越大：拉到底 `y` 变负，按钮矩形（正 y）再也命中不到 → 点击/高亮双失效。
- 修法：`on_mouse_move` 的 `btn` 改用 `pages::hit_header(x, screen_y)`（屏幕坐标，与 on_click
  同一份）；`tb`（窗口按钮，固定顶层）继续取 `pages::hit_test(x, y).1`。`hit_header` 只判
  头部两颗、仅硬件页 `cur_tab()==0` 有效，坐标语义注释已写清"调用方必须传未减 scroll 的
  screen_y，不可传内容坐标 y"。
- 验证（确定性、与数据量无关）：新增 smoke test `header_buttons_hit_uses_screen_coords_
  not_content_coords` —— ① 断言 `hit_header` 对两颗按钮都正确命中(0/1)；② **回归护栏**：
  断言旧逻辑 `hit_test(cx, cy - 5000).0 == -1`（滚到底按钮"消失"的 bug 签名），若修复无效
  此断言会立刻红。该测试不依赖 VM 显示/数据量，比一次性点按更稳。
- 临时改 `WIN_H=500` 复现窗口已还原 948；门禁全绿（fmt/clippy/275 tests，+1 新测试）；
  exe 682496B 部署 `dist/`。
- 真机复验建议（Z.W. 双击后看）：硬件页内容溢出 → 拉到底 → 仍点得到导出/截图、hover 有高亮。

## 第二十八轮：字体回退链——意外挖出真根因（FONT_UI 笔误 + NUL 尾巴比对 bug）
- 起点：为"雅黑创建失败回退宋体"加回退链（Z.W. 答复"加吧"）。`draw::font` 重写为
  候选链（首选 → Microsoft YaHei → YaHei UI → Segoe UI → 空名兜底），逐候选试建后用
  `GetTextFaceW` 核对真名，真名不在 `FONT_GOOD_FACES` 就 `DeleteObject` 换下一个。
- **根因①（历史遗留）**：`FONT_UI` 多打一个 `0x4E`（字母 N）→ "微软雅黑N"不存在 →
  GDI 静默换宋体。**VM + 真机全部从第一天就在用宋体**（r23 旧截图拉丁字母带衬线实锤）。
  去掉 `0x4E`。
- **根因②（本轮新发现，测试抓住的）**：`GetTextFaceW` 返回的长度**会把结尾 NUL 多算 1**，
  `from_utf16_lossy(&buf[..n])` 得到 `"微软雅黑\0"`，与 `"微软雅黑"` 精确比对**必败** →
  `face_accepted` 全部拒绝（含正确候选）→ 回退链一路漏到空名兜底 = 还是宋体。
  修法：`real_face` 统一 `trim_matches('\u{0}').trim()` 再返回。**教训：字符串 API 的
  "返回长度是否含 NUL" 必须实测验证，不能凭文档想当然**。
- 顺带修：`font()` 文档注释补空行（clippy `doc_lazy_continuation`）；测试自身的内联
  `GetTextFaceW` 查询同样要 trim（与 `real_face` 同一坑，两处都修）。
- 中文系统 `GetTextFaceW` 返回**本地化名「微软雅黑」**而非英文 "Microsoft YaHei"——
  `FONT_GOOD_FACES`（pub，测试共用同一份）必须两种都认，否则好字体被误杀。
- 验证：单元测试 `font_fallback_resolves_to_intended_face` 过（face = 微软雅黑）；
  门禁全绿（fmt/clippy/**276 tests**）；exe 684544B 部署 dist/。
- **VM 目视 A/B 定案**：r23 旧截图（宋体：Windows/QEMU/DIMM 字母带衬线、中文点阵感）
  vs 新截图 r28_font_shot.png（雅黑：无衬线、笔画圆润）——字体修复肉眼可证。
- 测试脚手架教训：新 `#[test]` 插错了位置（嵌进上一个测试函数体内）→ "never used" 警告
  + cargo test 找不到——**嵌套 fn 不被 test harness 收集**，加测试要确认在模块层级。

## 第三十轮：硬件页网卡分组只显示已连接（Z.W. 真机截图定案）

- 实现（纯 UI 过滤，不动采集层）：`build_hw_sections` 网卡分组先

  `OperStatus == IfOperStatusUp` 填（nic.rs），可靠。

## 本轮：低分辨率（1024×768）窗口显示不完整 + 2K/4K 自适应（用户："瞎子同事用 1024*768 运行后窗口显示不完整，2K/4K 会不会又太小，能按分辨率自适应吗"）
- **诊断结论**：
  - **2K/4K 已天然自适应、无需改**：进程声明 PerMonitorV2 + `scale()` 按 DPI 放大所有布局，
    系统缩放 >100%（2K/4K 默认 125%/150%）时文字物理尺寸与 1080p@100% 一致、不会变小；
    `WIN_W=593`/`WIN_H=948` 在高分屏只占一小块。仅「4K 且**手动**设 100% 缩放」会偏小
    （用户显式选择，标准 Windows 行为，不处理）——这点已如实告知用户。
  - **1024×768 是真 bug**：`CreateWindowExW` 用 `scale(WIN_H)=948`（96 DPI）建窗，而 768 屏
    工作区 ≈ 738；`center_window` 按「工作区正中」算 `y = work.top + (738-948)/2 = work.top -105`
    → 标题栏被推到屏外约 105px、底栏在屏下 → 看不见顶栏也拖不动。`WM_GETMINMAXINFO` 只钳
    「用户拖拽/最大化」尺寸、**不钳 `CreateWindowExW` 的显式尺寸**；`on_paint` 还把非磁盘页高
    重设成 `scale(WIN_H)`（同样超出）。根因 = 固定窗口高超过工作区 + 居中按设计高而非钳后高。
- **修法（统一钳到工作区，零回归）**：新增 `work_area()`（SPI_GETWORKAREA，per-monitor 感知下
  返回物理像素、与 `GetWindowRect`/`scale()` 同坐标空间）+ `max_win_w()/max_win_h()`
  （`=min(scale(WIN_*), 工作区)`），在五处复用：
  1. 建窗初始尺寸 → `init_w=max_win_w()`、`init_h=max_win_h()`（不再裸 `scale(WIN_*)`）；
  2. `center_window` → 算完 x/y 后 `clamp` 到工作区（`saturating_sub` 防极端小屏 debug panic，
     保证 `top>=work.top` 且 `bottom<=work.bottom`，标题栏不出屏、底栏不出屏）；
  3. `WM_GETMINMAXINFO` → 最小尺寸也 `min(scale(MARGIN*6)/scale(480), 工作区)`，避免极小屏
     （如 1024×600 上网本）最小尺寸反而超工作区；最大尺寸仍=工作区（防盖任务栏）；
  4. `WM_DPICHANGED` → 系统建议尺寸按 `max_win_*` 二次钳制（跨屏拖到更小显示器时不出屏）；
  5. `on_paint` 磁盘页自适应高度上限从 `scale(WIN_H)` 改为 `max_win_h()`（非磁盘页 `desired`
     也用 `max_win_h()`），小屏窗口高不超工作区、内容靠滚动条。
- **行为预期（1024×768）**：窗口 593×738，标题栏贴工作区顶、底栏贴底、整窗在屏内、内容滚动；
  2K/4K 文字物理尺寸不变、窗口按工作区钳制（永不撑爆/永不过小）。
- **防御细节**：`center_window` 用 `clamp(min, max)` 且 `max = work.left + (work_w).saturating_sub(w)`，
  保证 `max>=min`（w 已被钳到 `≤work_w`，正常不触发 saturating，仅保险极端退化）。
