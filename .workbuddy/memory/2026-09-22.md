## 概念澄清：内存 `speed_mhz` 是传输率不是时钟频率（Z.W. 问"6000 MT/s 是内存频率吗"）
- `speed_mhz` 字段存的是 SMBIOS Type17 `Speed` 的值（如 DDR5-6000 → 6000），**本质是数据传输率 MT/s，不是时钟频率**。
- DDR 双倍数据率：真实时钟频率 = 值 ÷ 2（DDR5-6000 → 3000 MHz）。SMBIOS/任务管理器把 MT/s 标成"MHz"是行业惯例混淆。
- 报告渲染层已正确标 `MT/s`（`lib.rs:302` 文本 / `lib.rs:743` HTML，均带注释说明），准确。JSON 字段名 `speed_mhz` 沿用 SMBIOS 命名惯例，**按纪律不动 core model**（保老存档/对拍兼容）。
- 资产盘点看 MT/s 这个数即可，无需换算 3000。聊天里勿把"6000 MT/s"叫"频率"，应称"内存速率/数据率"。

### 12:44 真因锁定 = 我引入的 bat 语法 bug（块内 echo 未转义括号）

- **是我上轮补丁引入的**：我在 report-failure / JSON-missing 分支加了 `echo ----- trace.log (exe stderr, incl. report step) follows -----`（3 处，第 80/98/106 行），裸括号未转义。原作者别处都规规矩矩用了 `^(` `^)`（130/142/165/166/187 行）。
- **修法**：把所有"块内 echo 带裸括号"的行改成方括号 `[]`（cmd 里 `[]` 无特殊含义）。涉及 6 行：42 / 80 / 98 / 106 / 171 / 188。顶层 echo 的圆括号（22/26/28/54/122/152）安全，不动。
- 复核：Python 扫描确认块内 echo 已无未转义括号；新 MD5 `9719b4bdc7cabe1e044c985e92d598c4`、6736B。
- **教训（写 bat 铁律）**：`if (...)`/`for (...)` 块内的 `echo`，任何 `(` `)` 必须转义 `^(` `^)` 或改用 `[]`；块边界被裸括号破坏会导致**静默提前终止**，报错信息还不指向真正的位置。此前几轮我误判为"拷贝没落地/环境问题"，实为自身语法 bug——**下次改 bat 后应先在能跑 cmd 的地方实测一遍**（本沙箱禁 cmd.exe，更要靠静态自查 + 用户侧一次实测）。

### 14:3x combase.dll 拦路石（Win7 加载最后一道关）
用户回传：X:\dev 拷了 win7 exe 后，报错从 `0xc0000005` 变成干净的缺 DLL 弹窗 **`combase.dll 丢失`**。PE 导入表全量 dump 坐实唯一 Win8+ 残留导入 = `combase.dll!CoTaskMemFree`（1 func）。
- **根因**：`windows` crate 0.62 把 `CoTaskMemFree` 的导入库指向 `combase.dll`（Win8+ COM 基础 DLL）。`CoTaskMemFree` 语义实现从 Win16 起就在 `ole32.dll`（OLE/COM 任务分配器），`combase.dll` 只是 Win8+ 转发宿主。Win7/2008R2 没有 combase → 加载失败。仓库显式 `use ... CoTaskMemFree` 在 `physical_disk.rs:49` / `memory_wmi.rs:23`（WMI/BSTR 字符串释放）。
- **修法（新增 `winsuitex-platform/src/win7_compat.rs`，仅 `--cfg winsuitex_win7` 编译）**：`#[no_mangle] pub extern "system" fn CoTaskMemFree(...)` 用自己的强符号覆盖 windows crate 引用，链接器因此丢弃 combase 导入；函数体**运行时** `LoadLibraryW("ole32.dll")+GetProcAddress("CoTaskMemFree")` 取到 ole32 真实地址再调用（`OnceLock` 缓存，首次后零开销）。
- **关键坑（已踩已修）**：第一版用 `#[link(name="ole32")] #[link_name="CoTaskMemFree"]` 静态声明，结果与 `#[no_mangle] CoTaskMemFree` 同名，链接器把 import 解析回本函数→**无限递归**且 ole32 真实实现没进导入表（导入表 ole32 不列 CoTaskMemFree）。必须运行时 GetProcAddress 切断同名纠缠。
- `HINSTANCE` 在 0.62 是 `*mut c_void` 包装（`.is_invalid()` 可用、`From<HINSTANCE> for HMODULE` 存在）；`LoadLibraryW` 返回 `Result<HMODULE, Error>`（不是裸句柄）。
- lib.rs 加 `#[cfg(winsuitex_win7)] pub mod win7_compat;`；platform/Cargo.toml 加 `[lints.rust] unexpected_cfgs` 声明避免 unexpected_cfgs 警告。Win7 构建 RUSTFLAGS 加 `--cfg winsuitex_win7`：`-C target-feature=+crt-static --cfg winsuitex_win7`。
- **验证铁证**：① PE 导入表 `combase` 计数 0、CoTaskMemFree 不再是静态导入；② 本机(Win10/11)跑 win7 版 exe `--version` 正常、采集 exit 0、JSON 正常；③ **A/B 同源码两 target 产物**：Win7-target 与 Win10-target 采集的 `inventory.json` 逐段比对（剥离 collected_at/build_time）除 `volumes.free_bytes` 因两次运行间隔磁盘写入漂移几百 KB 外，**硬件各段字节级完全一致** → 单一 win7 版 exe 在 Win10+ 行为等价，可作通用构建。
