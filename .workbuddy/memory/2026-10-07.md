## GUI 框架选型调研：longbridge/gpui-kit（Z.W. 问"用这个设计 GUI 如何"）
结论：**短期不迁，保留已修好的 egui 版；若要更现代观感，先做 spike 在真机验证 DX11 渲染再定。**
- 事实：Apache-2.0（商用无 copyleft，对持玛多分发友好）；`gpui-kit = "0.7"`（crates.io 单依赖，内 re-export GPUI+
  gpui-base+gpui-component+assets）；75+ 现成组件（表单/导航/图表/虚拟表格/代码编辑器/Markdown/SVG Lucide 图标）；
  **已用于 Longbridge Pro 公开商业桌面应用**（生产背书强）；风格 MD3/shadcn；自带 `system_monitor` 示例
  （实时 CPU/内存图表≈硬件仪表盘模板，可直接借鉴）。
- 范式差异：gpui-kit 是保留模式+响应式（`Render`/`div()`/`element`），与 egui 即时模式完全不同 → 切过去=整个 GUI crate 重写，
  现有"常驻采集线程 + update 轮询"模型要重新适配。
- **硬门槛（关键风险）**：GPUI Windows 后端需 **DirectX 11 GPU + 当前厂商驱动**，明确拒绝"Microsoft Basic Display Adapter"；
  Win10 1903+（用 IDXGIFactory6）。RDP/远程管理会话、驱动异常、VM 无 GPU 直通（本机 VM 即如此）均**起不来/白屏**——
  与 egui(wgpu 也需 GPU) 同源，但 gpui Windows 后端更年轻、已知坑更多（DirectComposition 部分 Win10 不兼容、ARM64 曾出问题）。
- 对 WinSuiteX 分发场景的隐患：网咖/电竞酒店客户机虽多为游戏独显（能跑），但**远程维护/无头/显卡驱动异常**的机器上 GUI 会直接打不开，
  正好重现"实机没数据"的失败模式；且 gpui-kit 0.7 极新、API 会大幅 churn，长期维护成本高于 egui。
- 澄清：「实机无数据」是逻辑 bug（只 load_json），**已修、与框架无关**；换 gpui-kit 不解决它。
- 建议路径：egui 版现已工作 + Ant 卡片已不丑，作为发货版；若 Z.W. 想要"wow"级现代观感且接受 DX11 前提+后续升级成本，
  用 gpui-kit `system_monitor` 模式写个小原型渲染 9 类硬件面板，**必须在真机（非 VM）验证 DX11 能起、启动鲁棒**，再决定是否迁移。
  core/platform 采集引擎框架无关、可整套复用，仅 GUI crate 替换。

## 战略重估：C++ vs Rust 发货版（Z.W. 实测后质疑 Rust）
Z.W. 原话：Rust 没达预期，体积/内存都比 C++ 大，UI 也不够鲜丽。实测数据支撑其判断：
- **体积**：Rust CLI `winsuitex.exe` 547KB ≈ C++ `WinSuiteX.exe` 508KB（几乎一样，Rust 引擎不胖）；
  但 Rust GUI `winsuitex-gui.exe` **5.66MB** vs C++ GUI（antd 699KB / ref 801KB）= **~8 倍**。
  故"Rust 大"实为 egui+wgpu GPU 框架之过，非 Rust 语言本身。
- **内存**：egui 即时模式每帧重绘 + 持 GPU 资源（顶点/图标纹理），比 C++ GDI 按需 WM_PAINT 高；
  绝对值不大（数十 MB），但对"低影响/瘦工具"产品哲学不符。VM 无法实跑测不了精确值。
- **UI 鲜丽**：C++ Ant 版（WinSuiteX_antd 1.3.5）是他认可的鲜丽参照；egui 手搓卡片偏平；gpui-kit 更鲜丽但 DX11 硬门槛+重写。
- **功能成熟度**：C++ 已 1.6.7，Rust GUI 才 1.0.4，C++ 功能更全——Rust 还差一截对齐。
结论（小雪研判）：对本产品"瘦+低影响+鲜丽单 exe"的价值观，**C++ GDI 是更契合的发货版**；
Rust 优势在开发效率/安全/引擎，不体现在发货产物上。建议：引擎/CLI/report 留 Rust（已瘦、安全、Z.W. AI 效率），
发货 GUI 回到 C++ GDI；这需重新打开"冻结 C++"红线（见 MEMORY.md 标注），待 Z.W. 拍板。
若硬约束"必须全 Rust 我能维护"，则只能接受 Rust GUI 体积/内存代价，或走 Rust+winsafe/GDI（≈用 Rust 重写一遍 C++ GUI，工作量巨大）。

## core-ui 调研补充（ghboke/core-ui，Z.W. 又点名调研）
- 事实：C++ 库 + 纯 C ABI（400+ 函数，uint64_t handle），MIT；渲染 **Direct2D/D3D11 硬件加速**，对齐 **Fluent 2** 设计语言；
  UI 用 `.uix` 单文件组件（Vue3 SFC 语法：<window>+<script>+<style>+<template>，QuickJS-NG 跑逻辑，无 DOM/无 Webview）；
  25-29 内置控件；静态链 ~2.2MB exe / 4.1MB DLL，空窗 <30MB、冷启 <200ms；Win10(1709+)，需 MSVC2019+/clang-cl，**MinGW 不支持**；
  作者果核（中文文档，1.8.0 活跃）。
- 对 Z.W. 三项抱怨：体积 ~2.2MB（远小于 egui 5.66MB，仍大于 C++ GDI 0.7MB）✅；内存 <30MB（D2D 高效，远好于 egui 持 GPU 场景）✅；
  鲜丽=Fluent2（比 egui 手搓/他 C++ Ant 都更现代）✅。
- 杀手锏（对他）：`.uix`=Vue 模板 + AI-native（llms.txt / uix-ai-guide / ui_debug_* 60+ + Named Pipe IPC 自验证），
  他几乎不写 C++（宿主仅 ~10 行 WinMain），UI 写 Vue/JS；Rust 引擎可经 C ABI 复用（extern "C" 导出采集函数，宿主接线）。
  这比 egui/gpui 都更契合他的 AI 辅助工作流。
- 风险（vs 他自己 C++ GDI antd）：① **D3D11 硬前提**——RDP/无头/基本显示适配器/VM 无 GPU 直通时可能起不来
  （与 gpui 同坑；D2D 或可走 WARP 软渲染但未明确保证），而 C++ GDI 无 GPU 也能画，更鲁棒；
  ② 外部依赖（单人中文项目，longevity 风险）vs 自有 C++ 资产零依赖；③ Rust↔core-ui C ABI 绑定 + 引擎导 C 接口 + 写宿主，有集成工作量
  （但 C ABI 是最易 FFI）。
- 结论：core-ui 是当前**唯一同时修复他三项抱怨且保留 Rust 引擎+AI 工作流**的候选；
  但 D3D11 鲁棒性 + 单人项目 longevity 是相对自有 C++ GDI 的劣势。建议 spike：Rust 引擎导 C ABI + 写 .uix 硬件面板 + 小宿主，
  真机（非 VM）验证 D3D11 能起、启动鲁棒，再与他 C++ GDI antd 并排比观感/体积，定夺。
- **Z.W. 关切"是否暗藏 Webview 占内存"——已确认不会**：README 明写 `no DOM, no Webview`；`.uix` 的 Vue 语法是"借壳"，
  由 core-ui 自带 `markup/` 解析器解析、用 **Direct2D 原生渲染**（CSS 子集/Flexbox 是 core-ui 自己实现，非浏览器布局引擎）；
  `<script>` 逻辑跑在嵌入式 **QuickJS-NG**（微型 JS 引擎，非 V8/Chromium，约数百 KB 级），无独立 webview 进程、
  无 Chromium DLL。空窗 <30MB 已含 JS 运行时，远小于 Electron 150MB+。架构等同 Qt/QML、Flutter（声明式 UI+原生渲染），
  非 Electron/Tauri(webview 套壳)。他现有 egui 版同样无 webview（纯 Rust+wgpu），core-ui 在这点上一样干净且更优。
  （唯一待验：<30MB 是作者声称，需真机实测；但架构上确无 webview 税。）

### 集成架构（已编译验证）
- 宿主 `src/main.rs`：① 动态 `LoadLibraryW("core-ui.dll")` + `GetProcAddress` 取 7 个符号

### windows 0.62 GDI/API 踩坑实录（首次编译 33 个错误收敛实录）
1. **`COLORREF` 是 tuple struct 不是 type alias**：`type Color = COLORREF` 后**别名不能当构造器用**，
   `rgb()` 里必须写 `COLORREF(v)`，写 `Color(v)` 报 E0423。也不能 `as Color` 强转（E0605）。
2. **`MebiBytes` 是 newtype**（`crates/winsuitex-core/src/model.rs:34`）：`total_mb.unwrap_or(0)` 连整数都报
   "expected MebiBytes, found integer"。取值必须 `.get()`（返回 u64），设计意图就是防单位误用。
3. **`SelectObject` 返回 `HGDIOBJ` 不是 `HANDLE`**：Backbuffer 的 `old_bmp` 字段类型必须是 `HGDIOBJ`。
4. **`SetBkMode` 恢复旧值**：返回 `i32`，回填要 `BACKGROUND_MODE(oldb as u32)`（typed enum，底层 u32）。
5. **`CreateDIBSection` 返回 `Result<HBITMAP>`**（0.62 起），要 `match`；`BitBlt` 源 DC 传 `Option<HDC>`。
6. **`DrawTextW` 只有 4 参**（不是 5 参），rect 需 `let mut rect = *r` 造可写副本。
7. **`CreateWindowExW` / `GetModuleHandleW` / `LoadCursorW` 全返回 `Result`**，
   `CreateWindowExW` 的 `hwndparent` 是 `Option<HWND>`（传 `None`，不是 `HWND_DESKTOP`）。
8. **`GetDpiForWindow` 在 `Win32_UI_HiDpi` feature 里**，不在 `WindowsAndMessaging`。
9. **`InvalidateRect` 首参是 `Option<HWND>`**；`DestroyWindow` 返回 `Result<()>`（`let _ =` 要留着），
   而 `PostQuitMessage` 返回 `()`（加 `let _ =` 反而触发 `let_unit_value`）——**同类函数不一致，必须逐个查**。
10. **不要用 `static mut` 存 UI 状态**：`static_mut_refs` clippy 会拦。改 `OnceLock<CollectResult>` +
    `AtomicI32/AtomicBool`，配 `cur_tab()`/`hover_tb()`/`snapshot()` 访问器函数，绘制侧全程安全。

### clippy 门禁修法（不是靠 `#[allow]`糊）
- `kv()` 8 参超限 → 抽 `KvLayout { x_key, x_val_end, font }`，调用降到 4 参。
- `card_end(hdc,left,right,y)` 三个参数没用 → 简化成 `card_end(y) -> i32`。

- 仅 `theme.rs` / `draw.rs` 保留 `#![allow(dead_code)]` 并写明理由（色板/原语先列全，
  后续右键页真开关会取用 `badge`/`card`）。

### 修复 3：内容超出窗口被裁 + 滚动钳制死锁
- 做法（不侵入绘制链）：**1×1 哑 DC 两趟法** —— 第一趟用 `Backbuffer::new(1, 1)` 建1px 内存 DC
  跑一遍页面绘制，页面函数改为返回内容底部 y；第二趟用 `OffsetViewportOrgEx` 上移+
  `IntersectClipRect` 裁剪，外面套 `SaveDC`/`RestoreDC` 成对恢复（否则污染底部栏绘制）。
  这样页面绘制函数不需要"干跑"开关，滚动条比例也拿得到真值。
- ⚠️ **踩坑：滚动钳制不能用 `fetch_add` 先累加再 clamp** —— 一旦被钳到 0，下一格又从 0 减，
  永远停在顶部（实测滚不动）。正确写法：读当前值 → 算 next → clamp → **写回**。
- `WM_MOUSEWHEEL` 的增量在 wparam 高 16 位（有符号）：`(wparam.0 >> 16) as i16 as i32` 得格数。
  验证脚本里发 `-12` 格要写`(x & 0xFFFF) << 16`（低 16 位是键状态，不是滚轮数据）。

## GDI 版第四轮：真机截图暴露的 4 个 bug + 双标题栏回归（本轮）

Z.W. 从真机发回 4 张截图（硬件页/右键页/磁盘页），无文字。逐张比对代码后识别出
**6 个 bug**（4 个是他截图里的，2 个是修第一个时发现的），全部已修 + 补了回归测试。

### 真机截图暴露的 4 个 bug（全部已修）
1. **内存空槽被当实插条渲染**：显示 `0 GB · DDR? · 0 MHz · [Empty]`，看着像故障。
   根因：`MemStick::is_populated()`（= `capacity_mb.is_some()`）存在但没被用，
   循环遍历了 `sticks` 全表。修法：`filter(is_populated)` 分 populated/empty，
   空槽汇总成一行"N 条未安装 + 位置"，不逐条展开。
   ⚠️ 第一版改漏了：汇总行改了，但**循环仍遍历全表** → 同一条槽位出现两次
   （截图里"已插 1 / 共 1 插槽" + "空槽 3 条"自相矛盾）。VM 截图才发现。
2. **伪字段拼装**：本机 SMBIOS 不给 `mem_type` / `speed_mhz` 时，硬拼成
   `DDR{}` + `{} MHz` → 显示 `DIMM 0 · 16 GB · DDR? · 0 MHz · QEMU`。
   修法：改 `Vec<String>` + `filter` + `join(" · ")`，**只拼有值的字段**。
3. **磁盘页"可用"列被右边框裁掉**：`colw = scale(78)` 写死，7×78=546 > 可用 513。
   修法：按权重 `[6,7,10,8,12,13,12]` 分配 `table_w`；容量两列右对齐（扫数字快）。
4. **磁盘页选中行锁死第一行**：`if i == 0` 写死 + `volumes.first()`。
   修法：`i as i32 == sel_vol()` + `volumes.get(sel_idx)`（越界回落第一行）。

### 修 bug 时发现的 2 个更隐蔽的 bug
5. **点击命中测试坐标系错配**（最隐蔽）：内容区绘制用了
   `OffsetViewportOrgEx(0, -scroll_y)`，所以**缓存的矩形是内容坐标系**，
   而鼠标 `lparam` 是窗口坐标系。症状 = "开关明明画在那里，点了没反应"。
   诊断抓手：打日志发现矩形 `top=203` 而点击 `y=246`，正好差 43px = 滚动量。
   修法：`on_click`/`on_mouse_move` 里 `let y = screen_y - scroll_y()`；
   **标题栏/页签在滚动区外，判它们必须用 `screen_y` 不是 `y`**。
6. **`col_x[7]` 数组越界 panic**：`let mut col_x = [0i32; 7]` 但每列取
   `col_x[i]` 与 `col_x[i+1]`，末列 i=6 时访问 `col_x[7]` → 切磁盘页就崩。
   修法：`const NCOL: usize = 7; let mut col_x = [0i32; NCOL + 1];`

### 冒烟测试（新建 `src/smoke_tests.rs`，4 个测试）
纯 GDI 自绘没有返回值检查，一个数组越界直接 panic，而 GUI 的失败模式极隐蔽

- `renders_with_missing_snapshot`：`None` 快照必须返回 0（不画半截内容）。
- `disk_row_hit_testing_covers_every_volume_exactly_once`：垂直扫描命中测试，

### ① "多了一层底" —— 自绘阴影是罪魁，直接删掉
- 根因：`theme.rs` 的 `SHADOW_PAD = 16`，窗口四周留 16px 画**自绘阴影**（三层实色矩形近似）。
  但 **GDI 无 alpha 通道**，三层实色叠出来是一圈**均匀的灰边**，不是阴影；而且三层绘制顺序写反，
  只剩最外层可见 → 视觉上就是"窗口里还套了一层底"。
- 更隐蔽的问题：描边画在**内缩 16px 的 body** 上，而窗口圆角是 `SetWindowRgn` 在**窗口边缘**裁的，
  两个圆角**不同心** → 这就是②"圆角是虚的"的真正来源之一。
- 修法：**`SHADOW_PAD: 16 → 0`**，`draw_window_frame()` 重写为「全窗铺 `C_BG` + 贴边描边」。
  窗口 = 内容矩形本身，圆角完全交给 `SetWindowRgn`。
- 常量**保留为 0 而不是删掉**：`body_pad()` / `content_top()` / `content_left()` / `content_right()`
  都引用它，留 0 让所有引用点自动归位，不必逐处改写（少一次大范围改动 = 少一次回归风险）。
- 实测窗口尺寸：**625×980 → 595×950**（正好各减 30 = SHADOW_PAD*2 减去圆角差），阴影留白消失。

### ② "圆角没有黑线，感觉是虚的" —— 描边色用错了
- 根因：窗口描边用的是 `C_BORDER`（`#D9D9D9`）。这个灰度是**给卡片用的**（卡片有白底衬托，
  浅边框刚好），但窗口直接贴在**任意桌面壁纸**上，`#D9D9D9` 几乎融进背景 → 看不出轮廓。
- 修法：`theme.rs` 新增 `C_WIN_BORDER = rgb(120, 120, 120)`（中深灰），窗口外描边专用。
  理由写进注释：**窗口轮廓是全应用对比度最高的一条线，必须保证在任何壁纸上都有清晰边界**。
- 实测：窗口右缘像素 = `(120,120,120)` ✅。

### ③ "三个自定义按钮也有问题" —— 两个独立 bug 叠加
**bug A：`WIN_CACHED_W` 初始化后从没更新过（恒 593）**
- `pages.rs` 里 `pub static WIN_CACHED_W: AtomicI32 = AtomicI32::new(WIN_W);` 定义后，
  全代码库**没有任何一处 `store`** → 永远 593。
- 而按钮的**绘制**位置用的是 `on_paint` 的真实客户区宽 `w`。绘制用 `w`、命中/hover 用 `WIN_CACHED_W`，
  两处一旦不同（resize 或 DPI 缩放后必然不同）→ **hover 高亮画到与鼠标错位的位置**。
  真机截图里按钮区域那块浅灰底，就是错位的 hover fill。
- 修法：`on_paint` 里加 `pages::WIN_CACHED_W.store(w, Ordering::Relaxed);`。
- **教训（写入 MEMORY.md 第四条铁律的延伸）**：凡是"绘制坐标"与"命中坐标"来自两个不同来源的静态量，
  必须有一处显式同步；静态缓存不更新是这类 bug 的经典形态，且症状是"看起来像样式问题"。

**bug B：缺 `WM_MOUSELEAVE` → hover 高亮永久残留**
- 鼠标移出窗口后没有消息清 hover 状态 → 按钮一直亮着。
- 修法：`WM_MOUSEMOVE` 里注册 `TrackMouseEvent`（`TME_LEAVE`），新增 `WM_MOUSELEAVE` 分支清
  `set_hover_export(false)` / `set_hover_tb(-1)` / `set_hover_switch(-1)` + `InvalidateRect`。
- ⚠️ **`TME_LEAVE` 是一次性的**：每次 `WM_MOUSEMOVE` 都要重新注册，只注册一次不生效。
- ⚠️ `WM_MOUSELEAVE`（值 **675 / 0x2A3**）在 `windows::Win32::UI::Controls`，
  **不在** `WindowsAndMessaging`；需要 `Win32_UI_Controls` feature。
  我第一版验证脚本发的是 0x2A2（错号），导致误判"残留没清"——**验证前先核消息号常量**。

### VM 实测结果

- 发 `WM_MOUSELEAVE = 675` → 按钮行浅灰残留 **0 px** ✅。
- 窗口右缘描边 `(120,120,120)` ✅。

### windows 0.62 frameless 相关 API 补充踩坑
- `CreateRoundRectRgn` 直接返回 `HRGN`（不是 Result），判 `is_invalid()`。
- `SetWindowRgn(hwnd, Some(hrgn), true)` —— 第三参是 `bool` 不是 `TRUE`；
  **SetWindowRgn 成功后 HRGN 归系统所有**，反复调用不泄漏，不要再 `DeleteObject`。
- `SystemParametersInfoW` 返回 `Result<()>`（判 `.is_ok()`，不是 `.as_bool()`）；
  第三参 `Option<*mut c_void>`（传 `ptr.cast()`）；第四参是 typed flags `SYSTEM_PARAMETERS_INFO_UPDATE_FLAGS(0)`。
- `TrackMouseEvent` 参数要 `*mut TRACKMOUSEEVENT`：`&tme as *const TRACKMOUSEEVENT as *mut TRACKMOUSEEVENT`。
- `WM_GETMINMAXINFO` 必须把 `ptMaxTrackSize` 限到工作区，否则 frameless 最大化会盖住任务栏。
- `WS_POPUP` 必须配 `WS_EX_APPWINDOW`，否则无边框窗口不进任务栏 / Alt+Tab 找不到。

## 第七轮：整窗紫蓝玻璃主题（Z.W. 发 6 张 C++/Rust 对照截图，未配文字）
Z.W. 贴了 C++ 版 v1.6.7（紫渐变）与 Rust GDI v0.1.0（灰白）三页对照图。
结论明确：功能对齐了，**观感差距是"主题级"的**——Rust 版还是 Ant 灰白底，C++ 版
是整窗紫蓝渐变 + 玻璃卡片。本轮把 C++ 截图做了**像素级采样**再照着实现。

### C++ 版采样结果（PIL 量的，不是目测）
- 整窗垂直渐变：`(135,81,238)`（顶）→ `(38,98,235)`（底）；
- 底栏实色 `(27,54,122)` 深藏青；窗口右缘描边 ≈ 叠白；
- 硬件页：**没有白卡片**——是一张"渐变上叠白 18%"的玻璃大卡 + 每个分组标题一条
  "叠白 10%"的亮带；**值文字白色、字段名淡紫白**（我一开始以为是深色字，放大裁剪后才确认）；
- 菜单页：**暗玻璃卡**（渐变上叠 ~50% 暗色，`(85,72,152)`），启用卡描边亮绿；
  按钮靛蓝 `(79,70,229)`；徽章灰紫半透明；
- 磁盘页：表格卡叠白 18%，**选中行薄荷绿 `(216,240,228)` + 深字**，详情卡叠白 30%。

### GDI 怎么做"半透明"（本轮核心技法）
GDI 无 alpha 通道，全部毛玻璃用**逐行混合**模拟：`draw::fill_glass[_round]`
每行取 `theme::grad_at(屏幕y, 窗口高)` 再 `over(base, 目标色, alpha)`。
⚠️ 必须**逐行**不能用固定色：长卡（硬件页 800px）用单一混合色，上下端和背景脱节。
⚠️ 混合取的是**屏幕坐标**的渐变色，页面绘制在 `OffsetViewportOrgEx(0,-scroll)` 视口里，
入参是内容坐标——所以每个页面绘制函数都要传 `scroll` 和 `win_h` 两个上下文。
⚠️ 顺带学到的采样方法论：**别在缩略图上猜文字颜色**。值文字在缩略图里看着像深色，
裁剪 2 倍放大后确认是白色。采样要裁剪放大 + 排除底色后数簇。

### pages.rs 硬件页重构（两段式布局）
玻璃卡是背景，必须先画，但高度取决于行数 → **先把数据整理成 `Vec<Section>`
（`build_hw_sections`，纯计算不碰 DC）→ 量总高 → 画玻璃卡 → 逐段绘制**。
副收益：布局算法只剩一处（量高和绘制用同一套增量），不会再有"量的高度 ≠ 画的"错位。

### 顺手修的三个数据/渲染问题（对照 C++ 版发现）
1. **CPU 行超宽截断**：型号串 40+ 字符再拼"4 核/4 线程·MHz"必然超宽，DrawTextW 单行硬裁剪。
   改成 C++ 版同款"型号 / 规格"两行；
2. **硬盘副行多余 "· 0 ·"**：标签 `硬盘#0` 已带序号，副行再拼 `d.index` 是重复——删；
3. **网络盘假 PD0 / 0 KB**：Z: 网络盘 `disk_index=None` 被 `unwrap_or(0)` 成 PD0、
   `cluster_bytes=0` 显示成 "0 KB"。改成 `None → "-"`、0 → "-"（`fmt_cluster` 读到
   <1KB 显示 "B"）；
4. **网卡行超宽截断**：MAC 拼进去必超宽，C++ 版本来就只显示 IP——对齐 C++，MAC 留在导出报告里。
