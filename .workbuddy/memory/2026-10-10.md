## 1024×768 真机崩溃 · 真实根因定位 + 修复（推翻上一轮"音频越界"假设）
- **拿到真机日志（Z.W. 贴回 diag 构建 `winsuitex-gui-gdi.log`）**：
  `CreateWindowExW: init_w=593 init_h=720 ...` → `PANIC at ...main.rs:600:65: min > max. min = 0, max = -2`。
  `on_paint enter` 从未出现 → 崩溃在 `CreateWindowExW` 内部同步消息派发（WM_CREATE/WM_SIZE），
  且 `main()` 503 行 `UpdateWindow` 强制同步 `WM_PAINT` 也在该窗口创建路径内；崩溃点≈`center_window` 的 `.clamp` 行（LTO 把 strip+release 的 file:line 错归因到 600，符号版修正后落在 `center_window` 内）。
- **推翻旧假设**：上一轮归因为"音频分组 `C_ACCENT_SOFT[7]` 越界 pages.rs:1015"——**错**。
  真机 panic 是 `clamp(0, -2)`，是 `center_window` 居中钳制，与音频/绘制数组无关。
  旧 0.1.7 带 `saturating_sub` 的居中代码**仍崩**，证明那条"修复"无效（见下）。
- **真实根因**：`center_window` 把窗口居中到工作区：
  `clamp(work.left, work.left + (work.right - work.left) - w)`。Z.W. 1024×768 **竖任务栏** →
  工作区宽 ≈593，而窗口宽 = `init_w(593) + 2*SHADOW_PAD = 595`（SHADOW_PAD=1）→ 工作区比窗口窄 2px →
  `work.right - work.left - w = 593 - 595 = -2` → `clamp(0, -2)` → release `panic("min > max")` 直接崩、无界面。
  即"窗口比工作区还宽 2px"这个窄工作区几何条件触发，与分辨率、音频都只是巧合共存。
- **关键认知纠错（铁律级）**：`saturating_sub` **只防下溢到 i32::MIN，不会把 -2 变成 0**！
  `500i32.saturating_sub(502) == -2`（不是 0）。所以旧代码 `work.left + (ww).saturating_sub(w)` 在 `w>ww` 时仍得负，
  clamp 照样 `min > max` 崩。这正是 0.1.7 修了还崩的根。
- **真正的修复**（`main.rs` `center_window`）：上界改用"右/下边缘坐标再 `.max` 兜底"，窗口比工作区宽/高时退化为贴左/贴上：
  `x = (...).clamp(work.left, (work.right - w).max(work.left))`；
  `y = (...).clamp(work.top, (work.bottom - h).max(work.top))`。（`.max(work.left)` 把上界拉回 `work.left`，
  使 `min==max`，绝不再出现 `clamp(min>max)`。）
- **实证（三层验证，杜绝假成功）**：
  1. 在 `center_window` 临时把 `(work.right-w).max(work.left)` 改回裸 `(work.right-work.left)-w`（复现旧 bug），

  2. 还原 `.max` 修复后再跑：窄工作区 `593×720`(恰好 -2) / `400×400`(窗口又宽又高) / `1920×1080`(正常) 全部
     `window created + shown`、无 PANIC → 修复确认。
