## GUI Win7 启动崩溃修复：GetSystemTimePreciseAsFileTime + DPI 整组 Win8+ 导入（15:07–15:50）
Z.W. 贴真机截图：`winsuitex-gui-gdi.exe` 弹「无法定位程序输入点 GetSystemTimePreciseAsFileTime 于动态链接库 kernel32.dll」——Win7/2008R2 上加载即崩。

### 根因（铁证）
- `dist/winsuitex-gui-gdi.exe`（0.5.5）是用**普通 `x86_64-pc-windows-msvc`（stable）**编的，IAT 全套 Win8+ 依赖：`GetSystemTimePreciseAsFileTime`(kernel32 Win8) + `api-ms-win-core-synch-l1-2-0`(std 的 WaitOnAddress) + `combase.dll`(CoTaskMemFree) + 一票 `api-ms-win-crt-*` + `api-ms-win-shcore-scaling-l1-1-1`(DPI)。9-22 的 Win7 通用化只做了 CLI，GUI 后来才大量开发、没走 win7 target。
- **windows-rs 按模块整块链接**：`Win32_System_SystemInformation` 里我们只用 `GetSystemInfo/GetTickCount64/GlobalMemoryStatusEx`（全是 Win7 既有），但模块里 Win8+ 的 `GetSystemTimePreciseAsFileTime` 被"连坐"写进 IAT——我们根本没调它。同理 `Win32_UI_HiDpi` 模块把 `GetDpiForMonitor/GetProcessDpiAwareness/SetProcessDpiAwareness`(api-ms-shcore) 连坐进来。
- GUI 比 CLI 多的雷：`main.rs:483` 直接调 `SetProcessDpiAwarenessContext`/`SetProcessDpiAwareness`/`GetDpiForSystem`/`GetDpiForWindow`（全 Win10）。

### 修法（同 CLI 先例：win7 target + `#[no_mangle]` 垫片）
1. `win7_compat.rs` 追加 9 个垫片（仅 `--cfg winsuitex_win7` 编译）：`GetSystemTimePreciseAsFileTime`（运行时探测真函数→退化 `GetSystemTimeAsFileTime`）+ 4 个 DPI 实函数（`SetProcessDpiAwarenessContext`/`SetProcessDpiAwareness`/`GetDpiForSystem`/`GetDpiForWindow`，探测真函数→Win7 回退 `SetProcessDPIAware`/96）+ 4 个被连坐但不调用的哑元（`GetDpiAwarenessContextForProcess`/`GetDpiForMonitor`/`GetDpiFromDpiAwarenessContext`/`GetProcessDpiAwareness`，只为丢弃 api-ms-shcore 导入）。运行时解析用 `load_fn(module, name)` 返回原始 fn 指针、调用点 transmute——**泛型 F 直接 transmute 编不过（E0512 依赖尺寸未知），必须调用点 transmute**。
2. 构建：`RUSTFLAGS="--cfg winsuitex_win7 -C target-feature=+crt-static" cargo +nightly build --release -Z build-std=std,panic_abort --target x86_64-win7-windows-msvc -p winsuitex-gui-gdi -p winsuitex-cli`。`rustup target add` 对 Tier3 报"无预编译产物"是预期——build-std 自编 std 不需要它。
3. 版本：GUI `version_stamp --root` → **0.5.6.20261027**（bump）；CLI `--set 0.1.0` 只刷日期戳（保 workspace parity）。

## PRINT 机（ASUS P8H61 + i3-3220）采集核查 + CPU 线程瞒报修复（18:20–18:55）
Z.W. 拷回 PRINT 机（Win10 Pro 22H2，i3-3220 / P8H61-M PLUS V3）三件套核查：GUI 导出 HTML + inventory.bat HTML/trace + inventory.json **三方数据逐字段一致**，11 源全 ok、零诊断降级， serial/SMART/boot_at 全齐——CLI 新 Win7 构建又过一轮真机。
- **坐实的 BIOS 脏数据（JSON 级证据）**：① 内存 ChannelB（真 4GiB）SMBIOS 返回 `vendor='0000' / part_no='[Empty]' / serial='00000000'`（SPD 未被 BIOS 读出，H61 混插常见）→ 待修展示层占位串归一；② `gpu[0].vram_mb=74`（GT 220 实际 512M/1G，Win10 老驱动 DXGI 谎报）→ 可选注册表 qwMemorySize 兜底；③ 渲染小瑕疵：GPU 行 Physical 类型时空段悬空 `·`；④ `usb.rs` 顶部模块注释与实现不符（实际只收 USBSTOR，USB=0 属预期）。
- **CPU 线程 bug 修复（Z.W. 指出"i3-3220 线程不对"）**：i3-3220 = 2C/4T，BIOS Type4 把 Thread Count 写成 2（`threads == cores` 不触发旧的"threads<cores"矛盾检查，`sanitize_thread_counts` 漏网）。修法：**OS 逻辑处理器总数与 SMBIOS 线程数不符时以 OS 为准、且只向上修正**（`per_socket > 现值 && per_socket >= cores` 才改）——多路服务器/空槽占位 Type4 的脏数据只会让均摊值偏小，向下改会改坏正确值（新增 `sanitize_never_shrinks_valid_threads` 用例钉死此纪律）。+3 测试（瞒报修正/不缩小/无 lp 保持），core 74 用例全绿。

### GPU 无驱动识别（Z.W. 问，已给方案待拍板）
现状：gpu.rs 只走 DXGI（+GDI 兜底名），无驱动时只会报"Microsoft 基本显示适配器"。可行方案：SetupAPI 枚举 PCI Display 类（GUID_DEVCLASS_DISPLAY）读 `SPDRP_HARDWAREID` → `PCI\VEN_x&DEV_y&SUBSYS_z`——**VEN/DEV 烧在芯片里，与驱动无关**，查内置表即得真实型号（SUBSYS 还能给板卡品牌）。工作项：① 仿 `pid_model_table` 用生成脚本从 pci.ids 抽 N/A/I 三家 GPU 条目（自动生成，防手误）；② gpu.rs 兜底链：DXGI 真名优先，Basic/Standard VGA 或空 → PCI 表填型号+品牌。等 Z.W. 拍板再动工。
