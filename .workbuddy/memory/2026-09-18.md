## 第二十轮：NVMe 序列号根因翻案 —— 不是句柄权限，是 IOCTL 被存储栈整体封禁（00:40–00:50）

### 关键纠正：上一轮的 RW 句柄诊断**只是表象，不是根因**

- 上一轮结论：NVMe 序列号取不到 = `query_nvme_serial` 复用了只读句柄（应为 RW）。
- **本轮用真机 JSON 的 `smart.source` 字段翻案**：4 块 NVMe 的 `source` 全是
  `StorageReliabilityCounter`（不是 `NvmeSmart`）。这说明 **property-query 与 protocol-command
  两条 `IOCTL_STORAGE_PROTOCOL_COMMAND` 路径在这台机器上双双失败**，温度只来自 WMI 兜底。
- 推论：NVMe Identify Controller 走的是**同一个 IOCTL**，所以即使修成 RW 句柄也必然同样被拒。
  RW 句柄该修（卫生问题），但**不是根因**。
- **方法论（可复用）**：判断某条采集路径为何失败时，先读**结果里的 `source` / 归因字段**，
  而不是猜实现细节。`source` 直接告诉你"哪条路真走通了"。

### 真正的修复：改用 WMI `MSFT_PhysicalDisk.SerialNumber` 兜底

- `ReliabilityInfo` 新增 `serial: Option<String>`；WQL 的 SELECT 加 `SerialNumber`；
  取值后过 `sanitize_disk_serial`（只拦控制字符 / >32 字符 / hex dump 形态，不误伤真实序列号）。
- `query_disk` 中新增兜底链最后一环：descriptor → (NVMe) Identify → **WMI**。仅在前两步都无值时启用。
  WMI 与 `DeviceIoControl` 是**完全独立的内核通道**，VMD 封 IOCTL 时它仍然可用。
- 盘索引映射复用已有的 `disk_index_from_path()`（已由温度回填验证过正确性）。

### 顺带修正一个"样本无效"的历史结论：WMI `PowerOnHours` 重新启用

- 原代码注释写「实测 PowerOnHours 恒为空」，但那次实测环境**整条 WMI 计数器路径都取不到数据
  （连温度都是空）** → 样本无效，据此放弃字段是错的。
- 现已重新启用：新增 `wmi_get_u64()`（**不能复用 `wmi_get_u16`**——`VariantToUInt16` 会把超范围值
  **静默钳位成 65535**，通电小时数动辄数万，会被污染成"看似合理的假数据"）。
- 真 0 按纪律判 None；`u64 → u32` 用 `try_from`（溢出即 None，不 wrap）。
- 加 `wmi_dbg` 打印计数器原始值，下一轮真机跑一次即可判定到底有没有值。

## 第二十一轮：找到真正的元凶 —— NVMe 命令 CDW10 偏移写错（00:55–01:05）

### 又是根因翻案：WMI 兜底也没值，逼出更深一层的排查

- 00:55 真机跑（新 exe 已含 WMI 兜底）：**NVMe 序列号仍 None，通电小时仍 None**。
  确认 WMI 兜底代码位置与逻辑无误（`query_disk` 第 463-479 行），即 `MSFT_PhysicalDisk.SerialNumber` 取不到。
- 沿"为什么 SMART 的 protocol-command 会失败"往上追，发现**真正的元凶**：

### ✅ 核心 bug：NVMe 命令的 CDW10 偏移写错（影响**所有** NVMe 透传，不只是序列号）

- NVMe 命令前 40 字节 = DW0~DW9（CDW0 / NSID / 保留×2 / MPTR / PRP1 / **PRP2**），
  **CDW10 位于 bytes 40..44**。
- 但 `build_nvme_get_log_page_cmd` 与 `build_nvme_identify_controller_cmd` **都写在 bytes 32..36**
  —— 那是 **PRP2** 的位置。后果：LID / CNS 全落进 PRP2，**真正的 CDW10 恒为 0**。
  - Get Log Page 变成「LID=0（Supported Log Pages）、NUMD=0」的畸形命令 → SMART/Health **永远**取不到。
  - Identify 同理 → 序列号永远取不到。
- **更糟的是：两个布局测试把这个错误偏移钉死了**（断言"DW10"在 32..36，并断言 `cmd[8..32]` 为 0），
  等于给 bug 加了保护壳。修实现的同时**必须一并改测试**。

### 排除项（查证而非猜测）

- 怀疑过 Windows `STORAGE_PROTOCOL_COMMAND` 头部字段偏移写错（我记忆里是
  `CommandInfo`16/`CommandLength`20）。**查微软官方文档后确认代码是对的**：
  实际布局为 `ReturnStatus`16 / `ErrorCode`20 / `CommandLength`24 / ... / Command 起于 80。
  上一轮踩坑（错误 317）后手工推导的布局正确，**不要凭记忆推翻**。
- 结论：87 错误**不是**命令内容导致（头部无误），而是该存储栈/驱动对
  `IOCTL_STORAGE_PROTOCOL_COMMAND` 整体不支持；CDW10 修好后能否放行，需真机验证。

### 本轮改动

1. 两个命令构造器：CDW10 写入位置 `32..36` → **`40..44`**，注释写明踩坑原因。
2. 两个布局测试改到 40..44，并**新增反向断言** `cmd[8..40]` 必须为 0 ——
   专门防止将来再把 CDW10 写回 PRP2 区间（把这次的教训固化成测试）。
3. WMI 采集处新增**清洗前原始值**日志（`SerialNumber 原始={:?} -> 清洗后={:?}` + `UniqueId`）——
   否则无法区分「WMI 没返回」与「返回了但被 sanitize 判废」，这两种情况的下一步完全不同。

## 第二十二轮：采集脚本易用化 + 堵死"新旧数据分不清"的坑（01:08）

### 起因

用户两点反馈：① 坚称自己发的不是旧数据；② 希望把 `set WSX_WMI_DEBUG=1` + 跑采集 + 拷日志
做成批处理，省得反复手工操作。

### 关于①的处置（不争辩，改为消除歧义）

- 我的依据：`inventory.json` mtime `00:24:07` < exe 部署时间 `00:30:03`。
- 但我发现旧 `inventory.bat` 的回拷是**静默 best-effort**：
  `copy /y "%JSON_OUT%" "%HERE%inventory.json" >nul 2>&1`。
  若被进程级过滤拦掉（bat 顶部注释本身就提到有这种过滤），dist 下就会**留着上一轮的结果**
  却看起来"刚跑过"——用户确实可能跑了新数据但没落盘。**两种可能都成立，不再纠缠，直接堵死。**

### 改动：两个批处理

1. `dist/inventory.bat`（重写）
   - 开头打印 exe 的 `--version` + **mtime + size**，一眼可辨跑的是哪份产物。
   - **回拷校验**：跑之前记录旧 mtime，跑完比对；未刷新就 `[WARN] 这是上一轮的旧数据`，
     并以 exit 3 显式失败、给出 %TEMP% 下的真实路径（不再静默）。
   - 打印 JSON 内 `collected_at`（数据自身时间戳，比文件 mtime 更权威）。
   - 支持 `inventory.bat debug` 开关。
2. `dist/inventory_debug.bat`（新增）：只有一行 `call "%~dp0inventory.bat" debug`，
   自动设 `WSX_WMI_DEBUG=1`、清掉旧日志、跑完提示把 `dist\wmi_debug.log` 一起发我。
   排查 NVMe 时双击这个即可。

### 坑：批处理中文编码

- 两个文件写入后编码不一致（一个 GBK+CRLF、一个 UTF-8+LF）——写入工具走了系统区域编码。
- 已统一为 **GBK + CRLF**，并在 `@echo off` 后加 `chcp 936 >nul 2>&1` 锁定控制台代码页，
  否则中文在 cmd 下会乱码。已抽样验证中文正常。
- **沙箱禁用 cmd.exe，无法实跑**；只做了静态括号平衡检查（17 开 17 闭，跨行块正常）与通读复核。

### 补记：批处理中文编码 —— GBK 方案被用户实测打回

- 上一轮我把两个 bat 存成 **GBK + chcp 936**（认为控制台是 cp936 最稳）。
- **用户实测反馈：用编辑器打开是乱码。** 原因：文件是 GBK，但编辑器按 UTF-8 解码。
  GBK 只保证"cmd 控制台能显示"，不保证"文件在编辑器里可读"——这是个只顾一半的方案。
- **改为：UTF-8 with BOM + `chcp 65001`**。BOM 让编辑器无需猜测即可识别；
  控制台切 65001 渲染 UTF-8。两头都对。
- 安全边界：bat 里**所有逻辑（标签/变量/命令/路径）都是 ASCII**，只有 echo/REM 文案是中文，
  所以即便代码页处理异常，也只影响显示、不影响行为。
- 待观察：个别老系统对 bat 的 UTF-8 BOM 处理有瑕疵（首行可能多出一个字符）。
  若用户报首行异常，退路是"bat 全 ASCII + 中文说明单独放 README"。

**教训（跨项目可复用）**：中文批处理不要只按"控制台代码页"来定编码——
文件还要被人用编辑器打开看。**UTF-8 BOM + chcp 65001 是 2026 年的默认解**，
且务必让脚本逻辑本身保持 ASCII，把编码风险局限在显示层。

## 第二十三轮：诊断日志到手 —— NVMe 序列号/通电时间**确认无解**，收口（01:20–01:26）

### 决定性证据（`dist/wmi_debug.log`，82 行）

1. **NVMe Identify：4 块盘全部 `IOCTL 错误码 87`（ERROR_INVALID_PARAMETER）**
   - 即使 CDW10 偏移已修正仍然 87 → **不是命令布局问题，是 Intel VMD 存储栈整体拒绝
     `IOCTL_STORAGE_PROTOCOL_COMMAND`**。这条路径在此机器上**无解**。
2. **WMI `MSFT_PhysicalDisk.SerialNumber` 有值，但 NVMe 全是合成 hex 垃圾**：
   - disk 0(SATA) `2CHMBDEP` → 采用 ✅
   - disk 1 `3633_5330_5240_1792_0025_3845_0000_0001.` / disk 2 `..._1232_...` /
     disk 3 `0100_0000_0000_0000_5CD2_E4FB_E063_5651.` / disk 4 `3631_3230_5810_6944_...`
     → 全部被 `sanitize_disk_serial` 正确判废。
   - `UniqueId` 全部为 None（空）。
   - **加"清洗前原始值"日志这个决定是关键的**：它区分了"WMI 没返回"与"返回但被判废"，
     否则会误判成 WMI 无效而白找新路径。
3. **`PowerOnHours` 属性存在，但 VMD 不填充 NVMe**：
   - disk 0(SATA) = **38831** → 与 ATA SMART 的 38830 差 1 小时，互相印证，说明字段本身可用 ✅
   - disk 1–4(NVMe) = **0** → `filter(|h| *h != 0)` 正确判为"未上报"。
   - 结论：上一轮"PowerOnHours 恒为空 → 放弃该字段"确实是**样本无效**导致的误判，重启用是对的，
     且已在 SATA 上拿到真值。
4. WMI 链路本身完全健康：`CoInitializeEx hr=0x0`、`process_is_elevated=Some(true)`、
   `ConnectServer 成功`、5 块盘命中、计数器各 1 条。

### 结论（可对外承诺）

**Intel VMD 下的 NVMe：序列号与通电小时数通过任何现有 Windows API 都拿不到。**
不是代码缺陷，是存储栈限制。工具对此是**如实留空**而非编造——符合"不许假成功"。

### 本轮改动：报告对缺失字段的说法要一致

- 原状：通电时长会显示"该存储栈未透传"，但**序列号那一行直接消失** → 用户会误读成"漏采"。
- 改为：当 `serial` 为 None 且 `smart.source` 是 `NvmeLogPage` / `StorageReliabilityCounter`
  （即被虚拟层遮挡）时，渲染 `序列号：该存储栈未透传`。
- 新增 2 个测试：`nvme_vmd_gap_shows_serial_transparency_note`（VMD 场景须明示）与
  `serial_transparency_note_not_applied_to_unmasked_disk`（非 VMD 场景不得乱贴，避免误导排查）。
- **刻意没做**：不去"解码"那串合成 hex 当成序列号——那正是一直在对抗的假数据。
  它虽是稳定标识，可作为「设备标识符」另列，但需用户定夺，未擅自加字段。

### 第二十三轮续：设备标识符稳定性 —— 发现"槽位相关的疑点"，暂不落地

- **跨运行稳定**：01:19 与 01:28 两次运行的 4 串 hex **完全一致**
  （disk1 `..._1792_..._0001.`、disk2 `..._1232_..._0001.`、disk3 `0100_..._5CD2_E4FB_E063_5651.`、
  disk4 `3631_3230_5810_6944_..._0002.`）。同一次开机内可复现。
- **但不能据此当资产 ID**：观察尾段——disk1/disk2 都是 `0000_0001.`，disk4 是 `0000_0002.`。
  **尾段疑似编码的是槽位/端口，而非盘自身**。若真如此，换插槽后 ID 会变，
  作为资产标识不仅无用、还会误导（恰恰是"换盘/挪盘"这个最需要它的场景失效）。
- **结论：暂不加该字段。** 要证实需做一次对照实验：把两块同型号三星 NVMe **互换插槽**再跑，
  看 ID 是跟着盘走（可当资产 ID）还是跟着槽位走（不可用）。
- **若要做，建议的稳妥形态**：先只进 JSON、不进 HTML 报告，明确标注"非序列号"，
  观察若干机器/重启后再决定是否提升为正式字段（避免污染与 C++ 版的逐段 diff 对齐）。
- 另注：`wmi_debug.log` 每次 exe 调用会**追加**一轮（bat 跑两次：--json 与 --report），
  所以日志里同一批信息出现两遍属正常，不是重复采集。

### 第二十三轮再续：设备标识符**已否决**（无需换插槽实验）

用户说明：远程作业，营业服务器不能随时换插槽 → 互换插槽实验不可行。
改为**纯数据分析定案**，结论：那串 hex **不能当资产 ID**，字段不加。三条判据（按字节拆解）：

```
盘              bytes0-7              bytes8-11        bytes12-15
disk1 SAMSUNG   36 33 53 30 52 40 17 92   00 25 38 45   00 00 00 01
disk2 SAMSUNG   36 33 53 30 52 40 12 32   00 25 38 45   00 00 00 01
disk4 ?         36 31 32 30 58 10 69 44   00 25 38 45   00 00 00 02
disk3 INTEL     01 00 00 00 00 00 00 00   5c d2 e4 fb   e0 63 56 51
```

1. **bytes8-11 三块盘完全相同**（`00 25 38 45`；Intel 为 `5c d2 e4 fb`）→ 是厂商/控制器常量，
   说明该 blob 混有非盘唯一信息，不是纯身份。
2. **格式不统一**：Intel 盘标识在后 8 字节、前 8 字节近全 0，与三星盘布局迥异。
3. 可打印部分仅 `'63S0R@..'` / `'6120X.iD'` 碎片，拼不出任何厂商序列号格式。
4. disk1/disk2 只差一个 16 位组（`1792` vs `1232`），尾段同为 `0001` → 尾段大概率是端口/槽位，
   换插槽即变 → 恰在最需要它的"换盘/挪盘"场景失效。

## WinSuiteX NVMe 序列号采集修复（AdapterSerialNumber）

- 线上核实（Dell/微软 KBA）：Windows Server 2016/2019/2022 上 `MSFT_PhysicalDisk.SerialNumber` 对 NVMe 返回的是 EUI64/NGUID（即 `3633_5330_…_0001.` 带下划线串），**真实打印序列号在 `AdapterSerialNumber` 字段**。
- 根因：原 `collect_storage_reliability` 的 WMI 查询未取 `AdapterSerialNumber`；`sanitize_disk_serial` 又把 EUI64 当伪值丢弃；NVMe Identify IOCTL 在 Intel VMD 存储栈被整体拒（error 87）。结果 4 块 NVMe 序列号全空。
- 修复（`rust/crates/winsuitex-platform/src/physical_disk.rs`）：① WMI SELECT 增加 `AdapterSerialNumber`；② `ReliabilityInfo` 增 `adapter_serial` 字段并解析；③ 序列号 WMI 兜底优先用 `adapter_serial`（再退回原 `SerialNumber`）。
- POH（通电时长）：经核实 `parse_nvme_smart` 解析逻辑正确（偏移 0x80=128 取 POH、0x70=112 取通电次数），但取数链路在 VMD 上被整体拦截（SMART 的 property-query / protocol-command IOCTL 均返 87），WMI 的 `StorageReliabilityCounter.PowerOnHours` 对 NVMe 本就返回 0——属**平台限制、代码无误**，未"假修"。需在目标机 BIOS 把 NVMe 由 VMD/RAID 切到标准 NVMe 模式，IOCTL 透传才会放行、POH 才会填充。
- 验证：cargo build --release 通过；`cargo test -p winsuitex-platform` 98/98 通过（含 sanitize 与 POH 解析单测）；`--selftest` 12/12；JSON 冒烟产出正常无 panic。新 exe 已同步 dist/winsuitex.exe（旧版备份 winsuitex.exe.bak_20260918_0834）。NVMe 序列号修复需在 SV-20260522YCII 真机重跑 `winsuitex --json` 确认 AdapterSerialNumber 填充。
