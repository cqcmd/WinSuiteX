## WinSuiteX Rust 重构 —— SMBIOS 解析 bug 修复 + 单位 newtype

### Bug 1：内存条恒为 0 根（根因：SMBIOS 字符串区终止符少算 1 字节）

- 现象：Rust `--report` 输出「内存条 0 根」，C++ 版正确显示「DIMM 0 16 GB」。
- 排查手法（可复用）：用 Python + ctypes 直接调 `GetSystemFirmwareTable('RSMB')` 把原始
  434 字节 dump 出来（脚本 `rust/_dump_smbios.py`），再用 dmidecode 风格遍历与 Rust 遍历
  **并排对照**，一眼看出在哪一条结构上分叉。比反复编译 Rust 快得多。
- 根因：`split_strings()` 在**无字符串**的结构上只消耗 1 字节，规范要求消耗 2 字节。
  本机 Type 16（物理内存阵列）恰好无字符串 → 整表错位 1 字节 → 把 `00 11`（终止符 +
  Type 17 的 type 字节）当成 `type=0 len=17` 的假结构 → 遍历提前 break，Type 17 永远到不了。
- 规范要点（DSP0134 §6.1.3）：字符串区**以双 00 结束**；有字符串时最后一串自身的 `\0`
  就是双 00 的第一个字节（只再多 1 字节），**无字符串时是完整的 2 字节 `00 00`**。
- 附带修正：`mem_type_name()` 的 DDR/DDR2 码位写错（写成 0x14/0x15），规范是 0x12/0x13，
  0x14 实为 DDR2 FB-DIMM。已改为完整规范表。
- 防复发：把本机真实 dump 存为 `winsuitex-core/tests/fixtures/smbios_qemu_q35_2026.bin`，
  加 6 条集成测试（遍历全结构、16GB 内存条、Type 0 在无字符串结构之后仍可解析等）。
  合成 fixture 测不出这类「我理解的规范 ≠ 真实固件」的缺陷。

### Bug 2：内存总计显示 16 KB（根因：MB 数值被当成字节）

- `fmt_bytes_int()` 只接受**字节**，报告层把 `total_mb`(MiB) 直接传进去 → 16384 被当字节。
- 修法（符合 Z.W. 要求的「用 newtype/类型系统表达不变量」）：新增 `MebiBytes(pub u64)`
  newtype（`winsuitex-core/src/model.rs`），`total_mb`/`capacity_mb`/`vram_mb`/`mem_used_mb`
  全部改用它；报告层新增 `fmt_mb` / `disp_mb`。此后 `fmt_bytes_int(&total_mb)` 编译不过。
- 刻意不实现 Add/Mul：容量只用于展示与比较，避免「两个 MiB 相乘」通过编译。

### 其它补齐
- `OsInfo.logical_processors`（`GetSystemInfo`），架构 `x86_64` → `x64` 归一
  （与 C++ 报告对齐，报告要能直接 diff）。
- CLI 新增 `--debug-smbios`（列结构清单 + 解析结果，区分「固件没给」还是「我们解析错」）
  与 `--dump-smbios <path>`（导出原始表，用于生成测试夹具）。
- 至此 OS / 主板 / CPU / 内存 / 分区 与 C++ 版**逐字一致**；显卡、显示器、物理硬盘、
  网卡仍缺（已派三个子代理并行实现）。

### 教训
- 解析固件/协议数据时，**用真实 dump 做 fixture** 比合成数据价值高一个量级。
- 单位（字节/MiB）这类"看起来不重要"的区分，正是 newtype 收益最高的地方。

### Bug 3：所有盘符都映射到 PhysicalDrive0（根因：结构体对齐）
- `IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS` 返回 `VOLUME_DISK_EXTENTS`，其 `Extents`
  起始偏移是 **8 不是 4** —— 因为 `DISK_EXTENT` 含 `LARGE_INTEGER`（8 字节对齐），
  `NumberOfDiskExtents` 后面有 4 字节 padding。手算偏移读到 padding → 恒为 0。
- 修法：改用 windows-rs 的 `VOLUME_DISK_EXTENTS` / `DISK_EXTENT` 强类型 + `Vec<u64>`
  分配保证 8 字节对齐，偏移交给编译器。**凡是手算 C 结构体字节偏移的地方都是雷区。**
- 验证：`C:→0`、`D:→1`，与 C++ 一致。

### 环境坑：显示设备枚举依赖会话
- `EnumDisplayDevicesW` 在无头/RDP 断连会话里**合法地返回 0 个设备**（`GetLastError=0`）。
  本次会话中途环境从"有显示器(1920×1080@32Hz)"变成"无显示设备"，C++ 版也同步变成"未知"。
- 因此**不要**在测试里断言"本机必有显示器"——那是环境假设，会让无头 CI 假失败。
  改为断言内部一致性（有显示器就必须能取到分辨率）。

### Rust 与 C++ 的**有意**差异（非 bug，已确认）
- 显卡：Rust 用 DXGI → 无头环境也能拿到 "Microsoft Basic Render Driver"；C++ 用 GDI
  显示适配器 → 此时为"未知"。且 DXGI 能列出 iGPU+dGPU 两块，C++ 只列挂桌面的那块。
- 网卡过滤：Rust 用"跳过 loopback + 无 MAC"的原则性规则，替代 C++ 的硬编码虚拟网卡名黑名单。

## 采集项补齐完成（CPU 代号 / USB / 音频 / 序列号 / 功能状态）

- **CPU 代号**：纯 Rust 实现（`crates/winsuitex-platform/src/cpuid.rs`），`core::arch::x86_64::__cpuid`
  读 leaf 0/1/0x80000002..4 + 自带代号表。本机实测 `Broadwell-E (Xeon)`，与 C++ 一致。
  **放弃 libcpuid FFI 的理由**：Rust 工具链是 `x86_64-pc-windows-msvc`，而 libcpuid 是 GNU-C
  （build.bat 注明"必须用 gcc 不能 g++"，含内联汇编），用 `cc` crate 会踩 cl.exe。
  结论：**技术选型要看工具链，不能照搬 C++ 的依赖**。
- **USB / 音频**：SetupAPI 遍历 + COM `IMMDeviceEnumerator` 判默认播放/录音（role 位）。
  `AudioSource.affinity() = MainThread`；`CoInitializeEx/CoUninitialize` 用 RAII guard 配对。
  本机 USB 拿到 `HID | USB 输入设备`，音频 0 条，与 C++ 基准一致。
- **序列号列**：是**物理盘**属性（`STORAGE_DEVICE_DESCRIPTOR`），按 disk_index 关联到分区行，
  不是卷属性。本机 QEMU 盘无序列号 → 显示"未知"（C++ 显示 "-"，属已记录的约定差异）。
- **功能状态小节**：报告层新增 `build_html_with_features(hw, volumes, &[(FeatureId, bool)])`。
  状态由调用方（CLI 读注册表）传入，**报告层保持纯渲染**，不越界读注册表。

### 修掉的 bug

## 报告对拍收尾（2026-09-15 晚）— 差异从 3 处收敛到 1 处

真机跑完对拍后逐项追根因，发现 3 处 DIFFERENT 里 **2 处是 Rust 侧的缺失/多出**，不是"有意差异"：

1. **内存条 Bank Locator 行缺失**：C++ `PutSmbStr` 对空字符串写"未知"，所以 bank 行恒存在；
   Rust 用 `Option` 且只在 `Some` 时渲染 → 整行没了。改为实插槽时恒输出 `opt_cell(&m.bank)`。
2. **内存类型多显示 "RAM"**：Rust 的 `mem_type_name` 按完整 DSP0134 表映射，0x07 → "RAM"；
   C++ `HwMemTypeToStr` 只映射 DDR 代际（0x12/13/14/18/19/1A-1E/22），泛化值返回空串。
   → 把 Rust 的展示集合收敛到与 C++ 一致，并留 TODO：LPDDR5(0x23)/HBM(0x20/21/24)
   是 C++ 缺的，要放开必须两边同步改，否则新笔记本上必然差异。
   **原则：展示层面的"更正确"如果会让每台机器都 diff 掉，就不是改进而是噪音。**
3. **序列号/卷标**：分区表空数据显示 "-" 而非"未知"（表格里 `-` 是惯例，也避免整段 diff）。

### 顺手修掉的真 bug
- **Extended Size 哨兵值**：`u32_le(0x1C)` 为 `0xFFFFFFFF`（= 未知）时，旧代码
  `v & 0x7FFF_FFFF` 会算出 2 TB 内存条。已加 `!= 0 && != 0xFFFFFFFF` 过滤 + 单元测试。
- **空插槽语义**：新增 `MemStick::is_populated()`（由 `capacity_mb.is_some()` 派生）。
  刻意**不加** `populated: bool` 字段——它与容量表达同一件事，两字段可能矛盾（非法状态可表示）。
  报告侧空槽渲染 `<span class="empty">空槽</span>`，与 C++ 一致。

### 结果
`compare_result.txt`：**same=10 different=1**（只剩显卡名，纯数据源差异）。
46 项单元测试 + 12 项自检全通过，`cargo fmt --check` 干净（顺手格式化了 main.rs 的历史遗留）。
release 二进制 373 KB。README/compare.ps1 的"已知差异"清单已同步更新为只剩 1 项，

### 13. 真机暴露 HID 产品串全空（根因：`open_hid` 用 `access=0`）— 2026-09-15

但**所有型号名都是空**（显示"未知输入设备"或"品牌(VAR:PID)"），且 A4Tech(09DA) 漏收显示"未知"。

#### 根因
`hid.rs::open_hid` 原用 `dwDesiredAccess=0` 打开 HID 设备。`HidD_GetProductString` 底层走
`DeviceIoControl(IOCTL_HID_GET_PRODUCT_STRING)`，**绝大多数真实 HID 设备要求 `GENERIC_READ` 权限**——
用 0 打开虽能拿到句柄，但取产品串被拒绝返回空 → 真机所有型号名丢失。

#### 修复
1. **权限改为 `GENERIC_READ.0`**：windows-rs 0.62 里 `GENERIC_READ` 是带 `.0` 的 u32 元组结构体
   （`GENERIC_ACCESS_RIGHTS(pub u32)`），不能直接传给 `CreateFileW(dwDesiredAccess: u32)`，
   必须取 `.0`。import 从 `Foundation` 引（不在 `FileSystem`）。
2. **防丢设备两级回退**：`GENERIC_READ.0` 打开失败（设备被独占）→ 回退 `access=0` 仍能拿句柄
   （仅取不到产品串，至少认得出 VID:PID/品牌），保证修完后**绝不比修前更差**（不会因权限拒绝整条丢失）。
3. **品牌表补 A4Tech(09DA)**：双飞燕/血手幽灵，网吧主力，原漏收 → 显示"未知输入设备"。

### 16. 终极缓解：让 cmd 写文件、exe 只输出到 stdout（过程-based 过滤绕开）— 2026-09-15

用户反馈即便 `%TEMP%` 备份版、非桌面目录 `D:\tmp\dist\` 仍被删。说明"新建文件被删"不是桌面专属，而是**按"winsuitex.exe 这个进程写盘"判定的过滤驱动**——无论写哪都删。于是换思路：

#### 关键洞察
当 `cmd` 执行 `winsuitex.exe --report - > file.html` 时，**文件是由 cmd.exe 调用 CreateFile 创建的（可信进程），winsuitex.exe 只往继承来的 stdout 句柄 write**。按"本进程写盘"判定的 minifilter 看到的是 cmd 创建了文件 → 不拦截。这是比"换目录/占位"更根本的绕开。

#### exe 改动（main.rs）
- 新增**标准输出模式**：`--json -` / `--report -`（path 为 `-`）= 把内容 `stdout.lock().write_all(bytes)` 落盘，且
  用 `write_all` 写**原始 UTF-8 字节**（不走 `print!` 的 locale 转码），保证与 `--json <文件>` 逐字节一致；
  摘要/降级信息改走 `eprintln`（重定向只截 stdout，stderr 仍上屏，不污染落盘文件）。
- 参数分发 bug：原 `Some(p) if !p.starts_with('-')` 会把 `-` 当成 flag 而回退默认路径 → 改为 `p == "-" || !p.starts_with('-')`。
- USAGE 补一行：路径可用 `-` 表示输出到标准输出。

#### bat 改动（dist/inventory.bat）
- 改为 `"%EXE%" --json - > "%TEMP%\winsuitex_inventory_%RANDOM%.json"` 与 `--report -` 同理 → 文件由 cmd 重定向落盘到 `%TEMP%`（C 盘，与 D: 工作目录不同卷，双重保险）。
- 每次写入后 `if errorlevel` + `if not exist` 仍自诊断（提示改"cmd 重定向也可能被拦"）。
- 再 `copy /y` 一份回工作目录（best-effort，若过滤器不盯工作目录则用户也能就地看到）。
- 最后 `start "" "%HTML_OUT%"` 打开 %TEMP% 副本。纯 ASCII。

#### 验证
- bat 纯 ASCII（non-ascii=0）；3 次隔离目录烟测均产出 `%TEMP%\winsuitex_inventory_*.json`(3047) 与 `*.html`(5355)，直接 `winsuitex.exe --json - > f.json` 验证为合法 JSON（top keys: info/volumes/diagnostics/features）。
- exe 编译通过；dist sha256 与 release 一致。
- **VM 里 exit 255 是沙箱 `start` 模拟的假码**（真实 Windows `start` 返 0），不影响双击运行。
- **真机（网吧机）复验待 Z.W.**：双击新 `inventory.bat`，报告应开在 `%TEMP%`。若仍被删，几乎可锁定为"按目录/文件名全局监控"（与创建进程无关），那时只能走 `--fs-probe` 量化 + 给 exe 数字签名加白 或 换不受监控的盘符。

### 17. Z.W. 反驳"过滤器论"后查出的 3 个真代码问题（"多台电脑都一样"）— 2026-09-15

Z.W. 反馈：肯定不是环境问题，其它电脑一样、没有防火墙。以此假设重查 bat/exe，**真查出 3 个问题**（他的直觉部分正确）：

1. **bat 是 LF-only 换行**（CRLF=0/63 行）——Write 工具写出的文件默认 LF。本机 Git Bash 调 cmd 恰好容忍，

2. **括号 bug 在错误路径复发**：`echo ... (exe exit nonzero).` 处于 `if errorlevel 1 ( ... )` 块内，

   已全部去掉块内 echo 文本中的括号，并用"假 exe（文本文件冒充）"专门触发错误路径验证：EXIT=1、报错正常。

## 20. 根因锁定：不是"文件被删"，而是**某个采集源把进程硬崩了** — 2026-09-16

Z.W. 回传 `probe_c.err`(120 B) + `probe_c.json`(0 B)，配合此前的 diag 结果，**推翻了全部"环境/文件系统"假设**。

### 决定性证据

**证据 1 —— stderr 缺最后一行。**
本地对照组 stderr 是两段（190 B）：`[nic] ...` + `JSON 已生成（已输出到 stdout…）`。
用户回传的只有一段（120 B）：**只有 `[nic] ...`，成功提示行不见了。**
代码里这两句之间没有任何分支会"跳过后半段"——唯一的解释是：**进程在执行到后面之前就死了。**

**证据 2 —— 死亡形式是无声硬崩，不是错误返回。**
- 没有 `序列化失败` / `写入 stdout 失败`（真出错都会 eprintln）
- 没有 Rust panic 消息（panic 会打到 stderr）
- ⇒ 是**进程级瞬死**（Windows 上典型为访问违规 `0xC0000005` 或栈溢出 `0xC0000409`），
  Rust 的 `catch_unwind` 捕获不到这类 OS 异常。

**证据 3 —— 为什么 stdout 是 0 字节（终于解释通了）。**
Rust 的 **stdout 带缓冲**（LineWriter），进程被硬杀时缓冲区内容**全部丢失**；
而 stderr **不带缓冲**，写一行落一行（这才有 `[nic]` 幸存下来）。
cmd 的 `>` 重定向会先建好空文件 → 进程死 → 文件永远停在自己 expr 的 0 字节。
所以"0 字节文件"不是"写入被拦截"，而是**进程死了**。

**证据 4 —— 凶手在哪个范围。**
`default_sources()` 顺序：`smbios → system → gpu.dxgi → display.gdi → **nic** → disk → physical_disk → usb → hid → audio`。
`[nic] …过滤后: 2` 是 NicSource **跑完**的汇总行 → 崩溃点在它**之后**：
`disk` / `physical_disk` / `usb` / `hid` / `audio` 五选一。

**证据 5 —— 反证"删除者"不存在。**
T1/T2（纯 cmd 写文件）PASS、T3（exe 自己的 fs-probe 写文件）5 秒后仍存活
⇒ 文件系统干净、没有 minifilter 删文件。**之前所有"按进程写盘被拦截"的推测全部作废。**

### 为什么虚拟机不复现
我的 VM 硬件简单，走不到那台机器的故障分支；用户机器（MSI B75MA-P45 等真实硬件）
的某设备/驱动返回了我们在合成环境里遇不到的数据。**这类 bug 只能靠真机 + 埋点，不能靠本地重跑。**

### 埋点方案（已实现，真机排障基础设施）

`crates/winsuitex-core/src/traits.rs`：
- **`WSX_TRACE=1`** → 每个源前后各打一行到 stderr：`[collect] >> <name>` / `<< <name> ok`。
  **刻意用 stderr**：无缓冲，进程哪怕下一秒硬崩，之前的行也已落盘 ⇒ 崩溃前最后一行即为凶手。

## 22. 【根因已修复】`hid.rs` 缓冲区按字节算、实为字符数 → 堆损坏 — 2026-09-16

### 决定性现象：崩点会移动
第二轮 crashtest（带堆自检的新 exe）回传：**崩点从 `audio` 移到 `hid`**
（`[heap] before hid ok`，`[heap] after hid` 没打印出来；`after usb` 是 ok）。

崩点漂移本身就是证据：**踩踏是"写越界"，检测是"后续分配/释放时才触发"**，
两者位置不一致。堆布局一变（本轮多了 HeapValidate 的分配），检测点就前移。
⇒ 真正的写入点在 `hid`（或更早），audio 只是上一轮的受害者。

### 根因：`RIDI_DEVICENAME` 的 size 单位是**字符数**，代码按**字节数**分配
`crates/winsuitex-platform/src/hid.rs::get_device_name`：

```rust
let mut buf = vec![0u16; (size / 2) as usize + 1];   // ← 错：把字符数当字节数
GetRawInputDeviceInfoW(..., RIDI_DEVICENAME, Some(buf.as_mut_ptr()), &mut size);
```

MSDN 原文（`GetRawInputDeviceInfoW` / RIDI_DEVICENAME 条目）：
> "For this uiCommand only, the value in `*pcbSize` is the **character count** (not the byte count)."

即第一次查询得到的 `size` 是**字符数**。代码却除以 2 分配（只分到所需的一半），
而第二次调用又把 `size` 原样传回当容量 → **API 认为可写 `size` 个字符（= `2×size` 字节），
实际缓冲区只有 `size+2` 字节 → 溢出约 `size` 字节**。

真机设备接口路径长约 90~110 字符 → 每次溢出约 90~110 字节，直接踩坏堆。

### 为什么三个现象全部对上
1. **只有真机复现**：`collect_input` 里 `if num == 0 { return Ok(Vec::new()) }`，
   VM 走 PS/2 仿真、Raw Input 枚举到 0 个设备 → 这段代码从未执行。
2. **崩点漂移（audio ↔ hid）**：溢出量随设备名长度变化，检测点在后续分配处才触发。
3. **无 panic / stdout 0 字节**：进程被堆管理器直接终止（0xC0000374），
   Rust 的缓冲 stdout 内容全部丢失。

### 修复（3 处）
1. **分配改为 `size + 1` 个 u16**（`device_name_buf_len()` 单独成函数以便单测）。
   该写法在两种解释下都安全：size 是字符 → 正确；size 是字节 → 多分一倍，无害。
2. **加尾部 8 个哨兵单元（0xA5A5）**：若 API 仍写了超过声明容量的数据，
   当场打印 `[hid] GetRawInputDeviceInfoW 写越界` 并丢弃该设备，
   **不再让越界写悄悄踩坏堆**。注意用调用**前**记录的 `declared` 做边界判断
   （`size` 是 in/out 参数，调用后可能被 API 改写）。
3. **回归测试** `device_name_buffer_is_sized_in_characters_not_bytes`：
   断言 `device_name_buf_len(90) == 91`（而非 46），锁死这条不变量。

### 验证
- `cargo fmt --check` = 0；`cargo clippy --all-targets --all-features -- -D warnings` 零 error/warning。
- `cargo test -p winsuitex-platform --lib` 通过（含新增回归测试）。
- release exe 444416 B，已同步 dist。

### 通用教训（高价值，可复用）
- **Win32 两步式 API（先查 size 再填缓冲）必须核对 size 的"单位"**：
  字节 / 字符 / **元素个数** 三者各不相同，甚至同一函数的不同 `uiCommand`
  单位都不一样（本例 RIDI_DEVICENAME 是字符，RIDI_DEVICEINFO 是字节）。
  不要凭"通常都是字节"的直觉下笔 —— 查文档原文。
- 分配公式单独抽成函数 + 单测，能让这类"单位错误"从"真机崩溃"降级为"编译期/测试期发现"。
- **早退守卫（`if num == 0 return`）会把整个模块变成测试盲区**，
  写 FFI 时要自问："这段代码在开发环境真的执行过吗？"
