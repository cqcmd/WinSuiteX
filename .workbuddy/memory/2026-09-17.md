## 真问题：NVMe SMART 在管理员下仍返回 None
- 4 块 NVMe（Samsung PM983 / Intel DC P4800X / Dell Ent）`smart.source=None`，原因串 `"需管理员权限或未返回 SMART 数据"`——该串只在 NVMe `DeviceIoControl(IOCTL_STORAGE_QUERY_PROPERTY)` **本身失败**时产生（property-query 路径）。
- 根因：企业级/数据中心 NVMe 在服务器存储栈下，property-query 路径常直接失败，而更通用可靠的 `IOCTL_STORAGE_PROTOCOL_COMMAND`（NVMe Admin Get Log Page, LID 0x02）能覆盖。

## 修复（`rust/crates/winsuitex-platform/src/physical_disk.rs`）
- NVMe 改为**双路径**：主路径 `nvme_query_property`（原 property-query，抽出为返回 `Result<Option<Vec<u8>>, u32>` 的辅助函数）；失败或无有效 log 时回落 `nvme_query_protocol_command`（新，发 Get Log Page 命令取 512 字节 SMART/Health log page）。

## 第三轮修复：找到 317 真因（windows 0.62.2 结构体布局错位）

## 第四/五轮修复：87 的真因 = `Length` 写成了 80（原生 sizeof 应为 84），并补齐 cmd_off 双尝试
- 11:42 真机复测（第三轮 11:28 部署版）确认 4× NVMe 全部：`property-query IOCTL 错误码 87，protocol-command IOCTL 错误码 87`。第三轮把 317→87，说明结构已不再被驱动当"无法处理"，但 87（`ERROR_INVALID_PARAMETER`）是**参数校验**阶段被拒。
- **更正第三轮关于原生布局的描述**（以 MSDN `ntddstor.h` 的 `STORAGE_PROTOCOL_COMMAND` 为准）：原生 Version=1 实际有 19 个 ULONG 字段（含 `DataFromDeviceBufferOffset`(52) / `FixedProtocolReturnData2`(68) / `Reserved1[2]`(72..80)），`Command` 的 `offsetof`= **80**，`sizeof`= **84**（80 头部 + Command[1] 1 字节 + 3 字节对齐填充）。`windows` 0.62.2 漏掉 `DataFromDeviceBufferOffset` 与 `FixedProtocolReturnData2` 且把 `Reserved1` 写成 `[u32;3]`，故其 `Command` 落在 76、`sizeof=80`——这是第三轮 317 的真正来源（已通过手工拼 buffer 绕过）。
- **87 的根因**：第三轮手工 buffer 把 `Length` 写成 80（误以为原生 sizeof=80），但驱动按 `sizeof=84` 校验 → 参数非法 → 87。命令放置位置也有两种合法约定：微软官方样例 / smartmontools 把命令放在 `sizeof(STRUCTURE)` **之后（=84）**；另一种是紧贴头部的 `offsetof(Command)`（=80）。不同存储栈只认一种。
- 修复（`nvme_query_protocol_command` 改收 `cmd_off: usize` 参数，手工 buffer 用 `w(4, cmd_off)` 动态写 Length、`buf[cmd_off..]` 放命令、`data_off=cmd_off+64` 放数据）：`query_smart_nvme` 兜底循环升为**三维**——NSID `[0xFFFFFFFF, 0]` × Flags `[0, ADAPTER_REQUEST]` × `cmd_off [84, 80]`，共 8 次尝试，任一成功即采用；失败诊断串带 `(cmd_off=N)` 便于判读。目的是**一次真机复测就穷尽两种命令偏移约定**，避免再多轮空转。

## 真机复测结果（12:06 复测，新 build 03:56:18 UTC）—— `cmd_off` 双尝试未解决，坐实存储栈层拦截
- 新 build 确已在真机运行：`collected_at 2026-09-17 12:06:39`（晚于部署 11:57），且诊断串首次出现 `(cmd_off=80)` 标记（仅本轮代码会输出），排除"跑错 exe"。
- 4 块 NVMe（Samsung PM983 / Intel DC P4800X / Dell 7.68TB）**全部**仍 `source=None`：`property-query IOCTL 错误码 87，protocol-command IOCTL 错误码 87（cmd_off=80）`。
- 推理：`query_smart_nvme` 兜底循环为 `cmd_off[84,80] × flags[0,ADAPTER] × nsid[0xFFFFFFFF,0]` = 8 次尝试，任一成功即 early-return。全部 4 盘都未 `source=NvmeLogPage` ⇒ **8 次全失败**。最终诊断停在最后一组（cmd_off=80），但能走到这里说明前 7 组也已失败 ⇒ **cmd_off=84（smartmontools 官方布局）与 cmd_off=80 都以 IOCTL 87 失败，且结果完全一致**。
- **结论**：`87（ERROR_INVALID_PARAMETER）` 与命令偏移/NSID/Flags 全部无关，且走完全不同代码路径的 `property-query` 也返回 87 ⇒ IOCTL 在本机**存储栈层被直接拒绝**，不是 buffer 布局 bug。代码已按原生规范拼出正确 buffer（Length/偏移都对），但平台不放行。
- **根因高度指向 Intel VMD / Inspur 固件层**：该 4× NVMe 服务器走 VMD，NVMe 盘以"VMD 托管命名空间"呈现给用户态，Windows 存储栈不向用户态透传 NVMe Admin 命令（连 ADAPTER_REQUEST 标志的适配器通道也一并拒绝）。属硬件/驱动/固件限制，非代码缺陷。
- **下一步（两条路）**：
  1. 高层 API 兜底：用 **Storage Management API / WMI `MSFT_StorageReliabilityCounter`**（PowerShell `Get-StorageReliabilityCounter`），这是与 `IOCTL_STORAGE_PROTOCOL_COMMAND` 完全不同的内核代码路径，在 VMD 下常能拿到 NVMe 的 Temperature/PowerOnHours/Wear(PercentageUsed)/读写错误计数。先让用户跑一条 PowerShell 探针确认该路径在真机可用，再决定要不要做成 Rust 集成（避免白写一轮）。
  2. 配置层兜底（末选、有风险）：BIOS 关闭 Intel VMD（NVMe 改 non-VMD/AHCI 或 RAID 模式）后用户态透传可能恢复，但会改变磁盘呈现、有数据/启动风险，仅作最后手段提及。
- **本次教训（已证伪的旧假设）**：不能想当然"命令偏移错→87"。87 与 cmd_off 无关说明是更上游的拒绝，应通过"多种偏移都试 + 看是否仍同一码"来快速判别是布局问题还是存储栈问题。

- **任务② 内存时序方案调研（结论：无现成免驱方案，接 LHM 类方案可行但代价大）**：
  - **结论速览**：Windows 下**没有**免管理员/免驱动的纯 Rust 或 Win32 API 能读到 CL/tRCD/tRP/tRAS。这些时序锁在内存条的 **SPD EEPROM（JEDEC，I²C/SMBus 地址 0x50–0x57）** 里，需要用户态直接操作 SMBus/I²C，而 Windows 禁止 Ring-0 I/O，必须走驱动级路径。
  - **系统自带接口的能力边界**（已逐一验证）：
    - `Win32_PhysicalMemory`（WMI/PowerShell）：仅给容量/速度/厂商/PartNumber，**无 CL**。`wmic memorychip get caslatency` 在多数机器返回空（属性基本不被填充）。
    - 任务管理器/msinfo32：仅速度，无时序。
    - 三者都**拿不到时序**，只确认"频率能正确采"（我们已采 `speed_mhz`）。
  - **现成可行方案（均为第三方驱动级）**：
    1. **LibreHardwareMonitor（LHM，MPL-2.0）**：最靠谱。其 `LibreHardwareMonitorLib` 通过内嵌的 `SmbusI801.bin` 等内核模块做特权 SMBus 读取，再按 JEDEC SPD 规范解析时序寄存器（字节18 CL、19 tCLns、20 tRCD、21 tRP、22 tRAS）。可作为 NuGet 库嵌入。代价：依赖 .NET Runtime（net8.0+）；要管理员权限；会注入内核模块（网吧环境需评估杀软/驱动签名白名单）。
    2. **CPU-Z / HWiNFO64**：最易用但闭源、GUI、需管理员，不适合我们单 exe 自绘方案直接调用。
    3. **纯 Rust 实现 SMBus 读取**：无成熟 crate；需自己用 `winapi`/`windows` crate 走 `\\.\物理内存` 或 PCI 配置空间（0xCF8/0xCFC）找 SMBus 控制器、发 I²C 读命令——即 CSDN 那篇 `winio` 老文的路子。工作量大、主板差异大、极易踩坑，**性价比低**，不建议自研。
  - **对网吧/电竞酒店的适配判断**：现代游戏（尤其 DDR5 + XMP/EXPO 高频内存）确实对时序敏感，但**换件匹配**通常只需"频率+类型+容量"（我们已满足），时序是"超频稳定性/性能调优"维度。若要做，性价比最高的落地是 **LHM 库嵌入方案**（需接受 .NET 依赖 + 管理员 + 驱动白名单评估）。纯 Rust 自研不推荐。
  - **待用户决策**：要不要上 LHM 类方案？若上，需先确认（a）目标机器允许 .NET 运行时、（b）杀软/驱动签名放行 LHM 内核模块、（c）是否只采 SPD 标称时序（JEDEC/XMP）还是也要实时运行时序。未动手，仅完成调研与可行性边界界定。

- **LHM 功能差距全景（用户追问"LHM 类方案还有哪些我们没有"）**：核心差异是**定位不同**——LHM 是「实时传感器轮询引擎」（持续 `Update()` 出温度/电压/风扇/功率时间序列），我们是「一次性资产/规格快照（inventory.json）」。逐项对比（✅=我们已有 ❌=我们没有），已据 platform crate 实际 `collect` 源核对：
  - CPU：❌ 每核/封装温度、负载%、实时频率、电压、封装功率（我们仅 型号+核/线程数）
  - GPU：❌ 温度、核心/显存频率、负载%、功耗、风扇、显存占用、热点温度（我们仅 名称+显存+厂商+类型，来自 `gpu.rs` DXGI/GDI）
  - 内存：❌ SPD 时序(CL/tRCD/tRP/tRAS)、XMP/EXPO、实时频率、条温（我们仅 SMBIOS 额定 speed/容量/厂商/PartNumber，见 smbios.rs Type17）
  - 主板/VRM/PCH/PCIe：❌ 所有温度、电压轨(+3.3/+5/+12/Vcore/DRAM…)、风扇转速+PWM 控制、SuperIO（我们仅 SMBIOS 主板型号+BIOS 版本/日期）
  - 风扇：❌ **完全零采集**
  - 存储：✅ 温度/健康/磨损%/通电时长（`physical_disk.rs` 已采，WMI `MSFT_StorageReliabilityCounter` + SATA SMART）；❌ 吞吐(read/write MB/s)、活动/负载%、剩余寿命趋势
  - 网络：❌ 实时吞吐/带宽利用率/链路速率（我们仅 `nic.rs` 适配器清单 名称/厂商/链路状态）
  - 电源/电池：❌（笔记本电池充放电/容量/损耗；网吧台式机基本 N/A）
  - **架构层**：❌ 我们无「持续轮询 + 时间序列 + 阈值告警」能力，只有快照。要做预警必须加采集循环，不是单次 inventory。
